# 게임 밸런스 수치 기획: 장별 사용 전략과 고급 활용

<a id="document-top"></a>

[README](../README.md) · [문서 지도](index.md) · [검수와 테스트](validation.md) · [프로젝트 사례](project-example.md)

이 문서는 포함된 `game-balance-bible` 스킬을 책의 8개 장에 따라 실무 설계·학습·장별 참고에 사용하는 방법을 정리합니다. 기본 요청 8개에 더해 **장별 고급 예시 32개와 후속 요청 8개**를 제공합니다. 필요한 상황을 골라 입력값을 바꾸고 결과를 다음 요청으로 이어갑니다. Codex에서는 `$game-balance-bible`, Claude Code와 Antigravity에서는 `/game-balance-bible`로 시작합니다. 아래 프롬프트의 `$`는 Codex 표기이므로 다른 호스트에서는 `/`로 바꿉니다.

> [!IMPORTANT]
> **원문 근거와 합성 예시**
>
> 책에서 정리한 개념·공식과 여기서 제안하는 작업 순서는 구분합니다. **`가정 예시`**라고 표시한 숫자와 상황은 이 가이드를 위한 새 예시이며 책의 사례가 아닙니다. 실제 프로젝트 값, 기간, 사용자군, 난수 규칙을 제공하고 결과를 별도로 검증해야 합니다. 이 가이드는 책의 모든 이미지·표를 완전하게 보존하거나 현재 서비스의 정답을 보장하지 않습니다.

## 사용 전에 정할 공통 입력

스킬에 숫자만 던지기보다 다음 정보를 함께 줍니다. 값이 없으면 스킬이 빈칸을 가정으로 명시하게 요청합니다.

1. **장르·목표 경험** — 장르, 목표 경험, 대상 사용자와 콘텐츠 구간을 적습니다.
2. **단위** — 단위를 고정합니다. 예를 들어 피해는 `1회 실제 피해`, DPS는 `초당 피해`, 비용은 `자원/단계`, 생산은 `자원/일`처럼 씁니다.
3. **기간·모집단** — 기간과 모집단을 고정합니다. 일일 누적값과 시즌 누적값, 전체 사용자와 결제 사용자 지표를 같은 열에 섞지 않습니다.
4. **계산 규칙** — 난수·반올림·초기값·상한을 적습니다. 순차 판정인지, 결과 칸이 100%를 나누는지, 첫 타격 시점이 언제인지가 결과를 바꿉니다.
5. **산출물** — 원하는 산출물 형태를 지정합니다. 표, 계산식, 변경안, 테스트 케이스, 장별 학습 노트 가운데 필요한 것을 말합니다.

각 장의 답변에는 가능한 한 **입력과 가정 → 계산·판단 → 조정안 → 검수 기준 → 다음 장 영향** 순서를 요구합니다. 읽을 자료는 [질문별 자료 지도](../.agents/skills/game-balance-bible/references/task-map.md)에서 찾습니다. 원문 근거가 필요한 수식·표는 [원문 페이지 지도](../.agents/skills/game-balance-bible/references/source-map.md)를 함께 확인합니다.

## 프롬프트를 고르고 결과를 이어가는 방법

1. **상황을 고릅니다.** 각 장의 기본 요청은 전체 구조를 잡고, A~D 예시는 특정 문제를 깊게 다룹니다. 새 기획은 1·2장, 전투는 3장, 보상·비용은 4장, 계산 검수는 5장부터 시작합니다.
2. **입력값을 바꿉니다.** `[입력]`은 실제 표·로그·메모로 채웁니다. `가정 예시`는 그대로 연습할 수 있으며, 실무에서는 게임의 값과 규칙으로 바꿉니다. 파일 경로를 쓰면 현재 에이전트가 접근할 수 있는 실제 경로를 제공합니다.
3. **결과를 확인합니다.** 예시 아래의 `결과 확인`으로 산식·합계·조건·누락을 점검합니다. 계산값이 맞아도 체감 밸런스는 별도 플레이 검증으로 확인합니다.
4. **후속 요청을 사용합니다.** 같은 대화에서 방금 나온 표·계산을 고쳐 비교합니다. 새 세션에서는 프로젝트 맥락, 입력 데이터와 이전 결과를 다시 제공합니다.
5. **다음 장에 전달합니다.** 예를 들어 3장의 성장 속성을 4장의 비용·보상에 연결하고, 5장에서 실제 도달 속성과 전투 결과를 검증합니다. [장 연결 흐름](#integrated-workflows)에 통합 요청도 있습니다.

### 여러 요청에서 재사용할 프로젝트 맥락

아래를 먼저 보내고 필요한 장의 요청을 이어 붙입니다. 목적이 단일 용어 설명이면 필요한 항목만 적습니다.

```text
$game-balance-bible
앞으로 다음 프로젝트 맥락으로 설계와 검수를 진행해줘.
장르·테마: [입력]
대상 사용자·세그먼트: [입력]
목표 경험·판정 기준: [입력]
콘텐츠 구간·관측 기간·시간 단위: [입력]
전투·성장·경제의 현재 데이터 또는 접근 가능한 파일: [입력]
고정할 규칙과 바꿀 수 있는 매개변수: [입력]
반올림·초기값·상한·확률 판정·첫 타격 시점: [해당 항목 입력]
답변은 책의 근거 / 프로젝트 데이터 / 가정 / 추가 제안을 구분해줘.
주제에 필요한 장과 참고 파일만 읽고, 사용한 파일·섹션을 밝혀줘.
원문 쪽수는 근거 파일에서 확인되는 범위만 적어줘.
없는 핵심 데이터는 무엇인지 밝히고, 가정으로 계산한 값은 확정값과 구분해줘.
```

### 원하는 깊이와 산출물을 지정하는 문장

| 목적 | 각 프롬프트 끝에 덧붙일 요청 |
|---|---|
| 학습 | “개념→작은 계산→오답 원인 순서로 설명하고, 연습문제와 해설을 별도 항목으로 만들어줘.” |
| 설계 | “변경 가능한 매개변수와 고정 조건을 구분하고, 최소 변경안과 대안의 차이를 비교해줘.” |
| 계산 구현 | “입력·중간식·단위·반올림을 표로 적고, 필요하면 의존성 없는 검산 코드를 제공해줘.” |
| 시뮬레이션 | “확정 계산과 난수 실험을 구분하고, 난수 시드·횟수·모형 가정·오차 범위를 기록해줘.” |
| 장별 참고 | “해당 장·공식 참고·용어집에서 근거를 찾아 설명하고, 확인되지 않는 원문 내용은 분리해줘.” |
| 수정 검수 | “변경 전후 차이와 영향받는 장을 정리하고, 통과 기준·실패 조건·미확인 항목을 남겨줘.” |

> [!NOTE]
> **요청과 실제 실행 구분**
>
> 이 표는 산출물을 요청하는 방법입니다. 프롬프트가 파일이나 코드를 요청해도 실제로 생성·실행됐는지는 응답과 도구 결과에서 확인합니다.

### 계산 결과를 실행 증거로 확인하기

숫자가 맞는 것과 계산 도구를 실제 실행한 것은 별도 확인 사항입니다. 검산이 필요하면 다음 요청을 계산 입력과 함께 사용합니다.

```text
$game-balance-bible
앞선 계산의 핵심 수치를 Python 또는 사용 가능한 계산 도구로 실제 실행해 독립 검산해줘.
입력·핵심 식·실행 방법·실행 결과·판정을 보여줘.
실행하지 못하면 미실행이라고 적고, 추론한 계산값을 실행 결과로 표현하지 마.
```

응답의 “검산했다”는 문장만으로 완료를 판단하지 않고 도구 호출·출력·오류와 최종 값을 함께 확인합니다. 일부 예시의 실제 실행과 관측 한계는 [프롬프트 표본 검증](validation.md#prompt-samples)에 기록합니다.

이 구분은 스킬의 [실행 검산 절차](../.agents/skills/game-balance-bible/patterns.md#계산-실행-검산--실무-보완)에도 반영했습니다. 공유 지갑·단계 조회를 검산할 때는 비용 제약을 만족하는 목록과 잔여량부터 확인하고, 조합 개수만으로 정확성을 판정하지 않습니다. 실행 오류를 수정했다면 재실행 출력으로 최종 상태를 판단합니다.

## 1장 — 수치 프로세스화: 변경을 하나의 시스템으로 다루기

### 사용할 상황

- 신규 성장 기능, 보상 이벤트, 난이도 조정을 동시에 검토해야 할 때
- 한 팀은 전투, 다른 팀은 경제를 담당해 변경 원인과 영향 범위가 분리될 때
- “보상을 올리면 좋아질 것 같다”처럼 결과만 있고 사용자 경험 목표가 불분명할 때

### 준비할 입력

- 변경하려는 기능, 해결하려는 사용자 경험 문제, 적용 콘텐츠와 버전 범위
- 준비·전투·경제·검증·수익화의 현재 입력과 산출물
- 기간, 사용자군, 성공 판정 지표와 되돌릴 수 있는 변경 단위

### 사용 전략

1. 5단계인 준비 작업 → 전투 수치 → 경제 수치 → 수치 검증 → 수익화에 현재 자료를 놓습니다.
2. 각 단계에 `결정`, `입력`, `산출물`, `검증 지표`, `다음 단계 전달값`을 한 줄씩 적게 합니다.
3. 변경값이 전투 보상·성장 비용·사용자 체감 중 무엇을 바꾸는지 화살표로 연결합니다.
4. 전투와 경제를 각각 계산한 뒤 같은 기간·같은 사용자 가정으로 5장에서 합쳐 검증합니다.
5. 수익화 요소가 있으면 매출 관련 결과만 보지 않고 핵심 루프의 부담과 진행 가능성도 되돌려 봅니다.

### 기본 요청 프롬프트

```text
$game-balance-bible
일일 던전 보상을 조정하려고 한다. 장르와 목표 경험은 [입력]이고,
현재 보상·성장 비용·몬스터 난이도·입장 상품 데이터는 [입력]이다.
1장의 5단계로 변경 전후의 입력·산출물·검증 지표를 표로 연결해줘.
값이 없는 항목은 가정으로 표시하고, 3~6장에서 재검증할 항목을 분리해줘.
```

#### A. 신규 프로젝트의 첫 수치 설계 지도

아직 표가 흩어져 있을 때, 목표 경험부터 검증 순서까지 한 장의 의사결정 지도로 만듭니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
신규 협동 PvE RPG의 첫 수치 설계 지도를 만들어줘.
목표 경험은 10분 세션에서 1회 성장 선택, 30일에 장비 1개 완성이다.
가정 입력: 일일 강화석 40개, 장비 총비용 1,200개, 보스 목표 처치 120초다.
유저군은 신규·일반·집중 플레이어로 나누고, 실제 비율은 아직 미확정이다.
1장의 준비→전투→경제→검증→수익화 5단계에 결정·입력·산출물·검증 지표를 배치해줘.
각 수치를 책 근거, 내가 준 입력, 추가 제안으로 구분해줘.
30일 장비 목표와 일일 공급의 관계를 계산하고 부족·초과 여부를 표시해줘.
전투 120초 목표를 계산하려면 아직 필요한 입력을 목록화해줘.
수익화는 설계 확정이 아니라 영향 확인 항목으로만 다뤄줘.
먼저 만들 표 3개와, 3~5장에서 이어 계산할 순서를 제시해줘.
성공 기준은 목표 주기·유저군·단위가 모든 표에서 일치하는 것이다.
```

</details>

> **확인 포인트**
>
> 결과에서 장비 비용 `1,200 ÷ 30 = 40개/일`이므로, 가정한 일일 공급만으로는 해당 장비 하나의 목표 주기와 일치하는지 확인합니다.

전투·보상·상점 담당 표가 따로 있을 때, 중복 공급과 빠진 소비처를 찾아 변경 전제부터 정리합니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible

현재 입력: 일일 던전 강화석 20개, 주간 퀘스트 70개, 이벤트 1회 100개다.
장비 강화는 주당 150개, 스킬 강화는 주당 80개를 같은 강화석으로 소비한다.
던전 보상은 전투 보상 표와 경제 생산 표에 각각 20개로 기록되어 있다.

3·4·5장에서 재계산할 값과 성공 기준을 변경 전후 비교 형식으로 적어줘.
```

</details>

## 2장 — 수치 구축 준비 작업: 숫자에 경험의 경계 조건 주기

### 사용할 상황

- 장르가 섞여 전투·성장·경제의 우선순위를 합의해야 할 때
- 타깃 게임을 참고하되 수치 복제를 피하고 싶을 때
- 콘텐츠, 수집, 난이도, 사회 기능 중 무엇이 대상 사용자에게 중요한지 정리할 때

### 준비할 입력

- 장르 구성, 테마, 핵심 세션과 장기 목표, 대상 사용자
- 성장·플레이·전투의 현재 기능 목록과 해금 조건
- 비교하려는 타깃 게임의 관찰 사실. 추측과 실제 관찰을 나눠 기록합니다.

### 사용 전략

1. 장르 이름을 하나로 고정하지 말고 각 요소가 책임질 경험과 측정할 결과로 분해합니다.
2. 테마가 약속하는 수집·전투·관계·자원 행동을 적고, 각 행동이 어떤 시스템에 연결되는지 확인합니다.
3. 사용자 관점의 넓이·깊이·난이도와 기획 관점의 성장·플레이·전투를 한 표에 놓습니다.
4. 타깃 게임은 `사용자/기획 목표 → 성장·플레이·경제 시스템 → 수익화` 순으로 역방향으로 읽습니다.
5. 비교 결과는 “가져올 숫자”가 아니라 “우리 프로젝트에서 검증할 가설”로 바꿉니다.

## 3장 — 게임의 전투 수치: 공식, 확률, 리듬을 분리해 설계하기

### 사용할 상황

- 공격·방어·체력, 치명·관통·회피, 스킬과 버프의 계산 순서를 정의할 때
- 직업, 몬스터, 보스의 생존 주기와 난이도를 역산할 때

### 준비할 입력

- 속성 정의, 공식, 적용 순서, 상한·하한·반올림, 스킬·버프 지속 조건

- 레벨·직업·과금 수준·몬스터 유형별 입력값과 비교 구간

### 사용 전략

1. 속성 정의 → 전투 구조 → 능력치 정량화 → AI/NPC 순서로 문서를 만들게 합니다.
2. 기초 플로, 스킬 플로, 대미지 플로에서 입력·출력·판정 순서·재진입 조건을 분리합니다.

4. 확률은 표시값이 아니라 경로 확률로 계산합니다. 순차 판정에서 앞 조건을 통과해야 하는 결과는 앞 조건의 확률을 곱합니다.
5. 전투력 합계와 DPS·생존·회복·제어 리듬을 별도 표로 보고, 마지막에는 전투 시뮬레이션으로 확인합니다.

### 가정 예시: 단위와 순서 확인

가정 예시로 공격력 `A=100`, 방어력 `D=100`을 책의 나눗셈 예시 `피해=A²/(A+D)`에 넣으면 1회 피해는 `50`입니다. 적 체력이 `1,000`이면 고정 피해 가정에서 필요 타격 수는 `ceil(1,000/50)=20회`입니다. 초당 2회 공격하고 첫 타격이 0초라면 처치 시각은 `(20-1)/2=9.5초`입니다. 이는 1회 피해·고정 간격·첫 타격 조건을 둔 가정 예시이며, 회피·치명·회복·행동 지연이 있는 실제 전투에 그대로 대입하지 않습니다.

### 산출물과 검수 기준

- 산출물은 속성 사전, 전투 플로, 구간별 피해·생존 표, NPC 보정안, 테스트 케이스입니다.
- 퍼센트 보너스가 중간식인지 최종식인지, 가산인지 곱연산인지 분명한지 봅니다.
- `HP/피해`의 단위를 턴·타격·초 가운데 하나로 고정했는지 확인합니다.

- 성장 분배는 동일 부모·속성별 예산에서 계층 비율을 곱하고, 강화 표의 누적 지급과 회차 지급을 구별합니다. [성장 분배 산식](../.agents/skills/game-balance-bible/references/combat-formulas.md#성장-구축분할세분화)을 함께 읽습니다.

### 다른 장과 잇기

3장의 성장 분배는 4장의 비용·보상으로 현실화되고, 5장은 그 결과로 실제 유저 속성 및 PvE·PvP를 검증합니다. 7장은 전투 시간·단일 피해의 변화가 리듬에 만드는 공백을 보고, 8장은 전투 기본 모델과 몬스터 난이도 모델의 연결을 명시합니다. 자세한 공식은 [전투 공식 참고](../.agents/skills/game-balance-bible/references/combat-formulas.md)를 확인합니다.

## 4장 — 게임의 경제 수치: 재화 총량과 가치의 계약 만들기

### 사용할 상황

- 강화 비용, 일일 보상, 이벤트, 드롭 테이블을 하나의 경제 흐름으로 바꿀 때
- 재화 부족·누적, 성장 모듈 간 비용 경쟁, 가성비 차이를 분석할 때
- 랜덤 보상이나 거래 가능 재화의 공급을 변경할 때

### 준비할 입력

- 화폐·자원 목록, 귀속/유통 여부, 생산 루트, 소비 루트, 환전·거래 규칙
- 성장 단계별 비용, 목표 주기, 일회성·반복 생산, 사용자군별 참여율
- 드롭의 가중치·확률·수량 분포·보장 조건과 가치 단위

### 사용 전략

1. 경제모델의 통제 수준과 거래 조건을 먼저 고르고, 화폐와 자원의 역할을 분리합니다.
2. I/O 표에 모든 생산·소비·판매·선물·이벤트·환전을 넣되 일회성과 반복 생산을 구분합니다.
3. 성장 소비 총량과 목표 주기로 일일 생산을 역산한 뒤 플레이별 공급으로 나눕니다.
4. 랜덤 보상은 가중치에서 실제 확률을 구하고, 수량·천장·다중 보상 조건을 분리해 기대 생산을 계산합니다.
5. 가성비 비교 전에 돈·시간·전투력 등을 하나의 가치 기준으로 환산하고, 증가계수와 사용자군별 참여율을 적용해 봅니다.

### 가정 예시: 기간과 총량 확인

가정 예시로 한 재화의 30일 총생산이 `3,000`, 같은 30일 총소비가 `3,600`이면 잔여량은 `-600`, 잔여 비율은 `(-600)/3,600=-16.67%`입니다. 이 비율의 분모는 소비이며, 소비가 0이면 정의하지 않습니다. 30일 생산과 1일 소비를 빼거나, 초기 보유량을 잔여량에 섞지 않습니다. 목표값은 게임·재화·세그먼트의 정책이므로 이 숫자를 보편 임계값으로 쓰지 않습니다.

### 기본 요청 프롬프트

```text
$game-balance-bible
[재화]의 생산·소비를 설계하려고 한다.
생산 루트와 기간별 수량은 [입력], 소비 테이블과 목표 주기는 [입력],
드롭·거래·이벤트·판매 조건은 [입력]이다.
4장의 경제모델→I/O→소비→생산→가치체계 순서로 표를 만들어줘.
반복/일회성, 귀속/유통, 확률/보장 조건을 분리하고,
같은 기간·같은 사용자군 기준의 기대 생산과 가성비 검수법을 제시해줘.
```

```text
$game-balance-bible
던전 보상 상자의 가중치 변경 전후 기대 공급을 검토해줘.
합성 풀: 강화석 4~8개가 가중치 50, 코인 100개가 가중치 30, 꽝이 가중치 20이다.
강화석 수량은 성공 시 4·5·6·7·8개가 같은 확률이라는 가정이다.
상자는 하루 1회 열고, 천장·보장·다중 보상·추가 드롭은 아직 없다.
변경안은 강화석 가중치 50을 40으로 낮추고 다른 가중치는 유지하는 것이다.
변경 전후 전체 가중치, 실제 획득 확률, 강화석·코인 기대 생산을 표로 계산해줘.
가중치와 고정 확률을 같은 것으로 취급하지 말고, 책 근거·제공 규칙·추가 제안을 분리해줘.
수량 기대값과 시도당 기대값, 성공 조건부 평균을 따로 표시해줘.
천장이나 다중 보상을 도입할 때 표준 풀에서 분리해 다시 계산할 필드를 적어줘.
4장 I/O와 5장 검증에 넘길 일·주·30일 기대 공급도 제안해줘.
성공 기준은 모든 결과 확률의 합과 변경 후 총 공급 변화가 재현되는 것이다.
```

</details>

> **확인 포인트**
>
> 검산하면 변경 전 총가중치 100에서 강화석 확률 50%, 시도당 기대 강화석은 `0.5×6=3개`; 변경 후 총가중치 90에서 강화석 확률은 `40/90≈44.44%`, 시도당 기대 강화석은 `≈2.667개`입니다.

#### D. 성장 가치와 가격을 같은 기준으로 비교하기

가격표만 비교하지 않고, 자원 비용·전투력 수익·플레이 비용을 공통 가치 기준으로 환산한 뒤 가성비의 용도를 한정합니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
장비 강화와 던전 플레이의 가치·가성비 비교 초안을 검토해줘.
합성 입력: 강화석 200개 단가 2, 코인 10,000개 단가 0.01, 강화 전투력 가치는 150이다.
별도 비교안은 강화석 600개 단가 0.5, 전투력 가치 150이며 코인 비용은 포함하지 않는다.
두 사례는 전제가 다르므로 같은 표의 합계나 직접 우열로 해석하면 안 된다.
4장의 공통 가치 기준→성장 가성비→플레이 가성비 순서로 계산표를 작성해줘.
각 값의 단위·출처·포함 비용을 명시하고, 책 근거·제공 입력·추가 제안을 구분해줘.
첫 사례의 총 소비 가치와, 두 번째 사례의 성장 가성비를 각각 계산해줘.
플레이 가성비를 계산하려면 시간·재료·사회 비용 중 무엇이 더 필요한지 적어줘.
가성비가 실제 재미·매출·평판을 증명하지 않는다는 한계를 검수 항목으로 넣어줘.
성공 기준은 분자·분모가 같은 가치 단위이고 서로 다른 전제를 섞지 않는 것이다.
```

</details>

> **확인 포인트**
>
> 첫 사례의 소비 가치는 `200×2+10,000×0.01=500`, 두 번째 사례의 성장 가성비는 `150÷(600×0.5)=0.5`입니다. 각 단가는 같은 가치 기준을 뜻하는 가정이며, 다른 수량·포함 비용의 전제를 섞지 않습니다.

</details>

### 산출물과 검수 기준

- 산출물은 자원 사전, I/O 표, 소비·생산 모델, 드롭 기대값 표, 가치 기준 표입니다.
- 같은 재화를 여러 성장 모듈의 가용량으로 중복 썼는지 확인합니다.

### 다른 장과 잇기

2장의 성장·플레이 구조가 I/O의 루트를 정하고, 3장의 속성 수익이 소비 모델의 가치 판단에 연결됩니다. 5장은 주기별 생산·소비·잔여와 도달 레벨을 검증하며, 6장은 수익화 변경이 이 흐름에 더하는 생산·소비를 따로 재검증합니다. 산식은 [경제 모델 참고](../.agents/skills/game-balance-bible/references/economy-models.md)를 확인합니다.

## 5장 — 게임 수치 검증: 유저 경로를 역방향으로 재생하기

### 사용할 상황

- 보상과 비용을 만들었지만 실제 유저가 어느 레벨·강화 단계에 도달하는지 불확실할 때
- 특정 레벨에서 난이도 급등, 재화 막힘, 사용자군 간 격차가 보일 때
- 전투식은 맞지만 경제·성장과 합친 실제 전투 결과를 확인할 때

### 준비할 입력

- 기간별 계획 생산과 추가 생산, 초기 보유량, 소비 우선순위와 모듈별 누적 비용
- 경험치·레벨 표, 해금 상한, 성장 모듈별 속성·전투력 표
- 세그먼트 정의, 몬스터 난이도 표, 전투 공식과 비교할 목표 결과

### 사용 전략

1. 생산 검증에서 계획 생산과 이벤트·퀘스트·상점 같은 추가 생산을 동일 기간으로 누적합니다.
2. 소비 검증에서 해당 시점에 접근 가능한 성장 모듈과 플레이 소비를 모두 합산합니다.
3. `잔여량=총생산-총소비`, `잔여 비율=(총생산-총소비)/총소비`를 같은 기준으로 계산하고, 소비가 0인 행은 별도 처리합니다. 실제 잔고는 `초기 보유량+유입-실제 지출`로 별도 추적합니다. 계획 소비가 공급보다 큰 음수 잔여량을 실제로 이미 지출한 음수 지갑으로 해석하지 않습니다.
4. 누적 경험치와 누적 비용을 오름차순 기준값 테이블에 퍼지 매칭해 도달 레벨·모듈 수준을 구합니다. 공유 재화라면 `모듈별 소비 합≤가용량` 제약을 먼저 적용합니다.
5. 그 유저 템플릿을 3장의 전투 모델과 몬스터 표에 넣고, 경제 → 성장 → 전투 결과의 인과를 기록합니다.

### 가정 예시: 공유 지갑의 제약

가정 예시로 강화석 가용량이 `100개`, 장비 한 단계 비용이 `20개`, 스킬 한 단계 비용이 `10개`라면 `20×장비 단계 + 10×스킬 단계 ≤ 100`이어야 합니다. 장비 5단계와 스킬 10단계는 `200개`를 요구하므로 동시에 도달했다고 계산할 수 없습니다. 각 모듈을 독립적으로 최고 단계에 퍼지 매칭하기 전에 배분 정책·우선순위를 정해야 합니다.

### 기본 요청 프롬프트

```text
$game-balance-bible
[기간] 동안 [사용자군]의 실제 성장 경로를 검증해줘.
계획/추가 생산, 초기 재고, 소비·경험치·레벨·성장 모듈·몬스터 데이터는 [입력]이다.
5장의 경제 검증→레벨 검증→성장 검증→전투 검증 순서로 계산 표를 제안해줘.
누적 기준, 퍼지 매칭의 정렬 조건, 공유 재화 제약, 0 소비·상한 초과 경계를 명시하고
세그먼트별로 원인과 조정 후보를 분리해줘.
```

```text
5장의 경제→성장→전투 역방향 검증을 작성해줘.
가정상 14일 차에 전사와 궁수 모두 공격력 120, 방어력 90, 체력 300에 도달한다.
PvE 적은 방어력 100, 체력 600이고 단순 피해식은 공격력−방어력, 최소 피해는 1이다.
두 직업의 공격 속도는 초당 1.5회, 첫 타격은 0초, 치명·회복·회피는 없다.
PvP는 상대 방어력 90, 체력 300으로 두 직업을 같은 조건에서 비교해줘.
타격 수는 올림 처리하고 처치 시각은 (타격 수−1)/공격 속도로 계산해줘.
생존 턴 비율과 1회 피해 비율을 함께 쓸 때는 서로 다른 열·식으로 분리하고, 원문 표5.15의 피해식이 이 단순식으로 재현된다고 주장하지 마.
이 결과가 직업 밸런스인지 동일한 입력의 산술적 동률인지 구분하고, 실제 차이를 검증할 추가 속성도 적어줘.
14일 차 속성이 경제 생산·소비에서 왔다는 가정과 책 근거인 검증 순서를 분리해줘.
산출물은 PvE/PvP 표, 단위, 성공 기준, 회귀 테스트 경계값으로 구성해줘.
```

</details>

### 산출물과 검수 기준

- 산출물은 기간별 생산·소비·잔여 표, 레벨·성장 모듈 매핑, 유저 템플릿, 전투 결과 표입니다.
- 누적 생산에서 일일 소비를 빼는 등 서로 다른 기간을 섞지 않았는지 봅니다.
- 퍼지 매칭 기준 열이 오름차순인지, 최저·최고 구간과 초기 경험치를 처리했는지 확인합니다.
- 모든 사용자군에 같은 성장 경로를 강제하지 않고 활성·소과금·중과금·헤비 등 실제 세그먼트 정의를 적용합니다.
- 전투 실패가 공식 문제인지, 실제 도달 속성·보상·비용 문제인지 분리합니다.
- 비용 행이 현재 레벨까지의 누적값인지 다음 도달 레벨 비용인지 고정합니다. 원문 표5.15의 ‘생존 비율’은 각주상 1회 피해 비율이므로 생존 턴 비율로 자동 치환하지 않습니다. 원문 레벨값·그래프 범례의 불일치는 [조회·검증 조건](../.agents/skills/game-balance-bible/chapters/ch05-validation.md#검증-표의-연결-계약)과 원문 지도에서 확인합니다.

### 다른 장과 잇기

5장은 1장의 전체 루프에서 수정 결정을 만드는 관문입니다. 3장에 유저·몬스터 템플릿을 되돌리고, 4장의 생산·소비 가정을 고치며, 6장의 충전·소비 변경을 같은 경로에서 검증합니다. 7장에는 시간축 결과를 단계 목표와 리듬 그래프로 넘깁니다.

## 6장 — 게임의 수익화: 지표·결제·소비가 경험을 바꾸는 경로 확인하기

### 사용할 상황

- 상품·충전·뽑기·유도 결제의 위치와 게임 내 소비를 검토할 때
- ARPU, ARPPU, 결제율, LTV, CPA 등 지표를 하나의 보고서에서 비교할 때
- 결제 변경이 성장 격차, 경제 잔여, 전투 리듬에 미치는 영향을 분석할 때

### 준비할 입력

- 수익화 포지셔닝, 상품·가격·지급물·사용처·보장 조건, 변경 전후 기간
- 지표 정의, 모집단, 집계 기간, 제외 사용자, 통화·환불 처리 기준
- 충전 사용자군과 게임 내 소비 데이터, 성장·경제·전투 검증 결과

### 사용 전략

1. 경험·성장·기능·화폐 결제 가운데 변경이 무엇을 제공하는지 먼저 분류합니다.
2. 충전과 게임 안에서의 소비를 별도 흐름으로 적습니다. 구매량이 늘어도 실제 소비처·가치 체계가 바뀌지 않을 수 있습니다.
3. 각 지표에 분자·분모·모집단·기간을 붙입니다. 예를 들어 결제자 평균과 전체 사용자 평균을 섞지 않습니다.
4. 무료·소과금·고과금 같은 사용자군별 성장 경로와 경제 잔여를 비교하고, 전투 격차를 5장에서 다시 확인합니다.
5. 이벤트형 상품은 책의 5단계 운영법에 따라 목적 → 형식 → 참여 조건 → 주기 → 콘텐츠를 정의합니다. 월간 패스와 순위 이벤트를 비교한다면 목표 지표, 참여 횟수, 보상 소모 기간을 각각 적습니다.
6. 결과가 좋거나 나쁘다는 결론 전에 수익화가 핵심 플레이를 앞당기는지, 막는지, 선택을 넓히는지 확인합니다.

### 기본 요청 프롬프트

```text
[상품 또는 수익화 변경]을 검토해줘.
```

```text
$game-balance-bible
6장의 5단계 운영법으로 7일 성장 패스 가정안을 검토해줘.
목표는 활성 이용자 결제율(PR) 변화 관찰 하나이며, ARPPU나 순위 경쟁은 성공 지표에서 제외한다.
대상은 튜토리얼 완료 후 7일 이내의 활성 이용자, 참여 조건은 패스 1회 구매다.
보상은 즉시 성장 재화 100과 매일 재화 20×7일이며 단위는 재화/계정이다.
이벤트 목적·형식·참여 조건·주기·콘텐츠를 표로 고정하고, 각 항목의 실패 신호를 적어줘.
무료 진행을 막지 않는지 판단할 실제 진행·이탈·경제 데이터가 없다는 점을 가정으로 표시해줘.
PR의 분자·분모·7일 관찰 기간과 대조군 정의를 제안하되 효과를 사실처럼 단정하지 마.
책의 5단계 프레임과 이 이벤트 숫자·운영안은 구분하고, 성공 기준과 중단 기준을 함께 작성해줘.
```

</details>

> **확인 포인트**
>
> `100+20×7=240` 재화인지와 PR 외의 목표를 몰래 합쳐 평가하지 않았는지, 대조군과 기간이 명시됐는지 확인합니다.

<a id="ch06-d"></a>

#### D. 충전량과 게임 내 소비 압력을 분리하는 영향 분석

상품 지급이 늘어도 성장 소비처와 전투 격차가 어떻게 바뀌는지 자동으로 알 수 없을 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
6장 충전 검증과 소비 검증을 분리해 분석해줘.
가정상 소과금 결제자는 상품으로 다이아 500을 받고, 7일 목표 소비에는 다이아 620이 필요하다.
차액은 획득 다이아−필요 다이아로 계산하고, 모든 수량은 다이아/7일/결제자 1명 기준이다.
차액, 부족량, 충전 검증에서 필요한 상품·구매 데이터, 소비 검증에서 필요한 사용처 데이터를 각각 표로 작성해줘.
부족 120을 가격 인상이나 강제 결핍의 근거로 결론내리지 말고 선택성·무료 진행·이탈을 검증할 항목으로 분리해줘.
5장에 넘길 경제 잔여, 도달 성장, PvP 격차 입력과 3장에 넘길 전투 입력을 명시해줘.
책의 push/pull·차액 개념과 이 수치가 가정이라는 사실을 구분하고, 반올림 없이 정수로 처리해줘.
산출물 마지막에는 충전 변화와 소비 변화 중 무엇이 관측값인지 확인하는 질문을 넣어줘.
```

</details>

> **확인 포인트**
>
> 차액 `-120`, 부족량 `120`인지와 부족을 구매 강제의 정당화가 아니라 후속 검증 가설로 다뤘는지 확인합니다.

#### 결과를 이어서 개선하는 후속 프롬프트

앞선 KPI·상품·이벤트·소비 표에서 특정 가설만 수정해 비교하고, 지표 상승과 경험 악화를 함께 검증할 때 사용합니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
바로 앞 6장 분석 결과를 입력으로 사용해 두 개선 시나리오를 비교해줘.
실제 구매·이탈·성장 데이터가 없는 값은 가정 A/B로만 두고 새 사실을 만들지 마.
유지할 모집단, PR·ARPPU·ARPU의 분모, 관찰 기간, 환불·통화 처리 규칙을 먼저 선언해줘.
각 시나리오의 직접 충전, 게임 내 소비, 부족량, 경제 잔여, 성장 도달, PvP 영향 경로를 분리해줘.
근사 LTV는 이탈률이 0이 아닌 경우에만 참고치로 계산하고 장기 예측으로 단정하지 마.
5단계 이벤트라면 목적 하나와 대조군·중단 기준을 유지해줘.
책 근거, 프로젝트 가정, 실제로 수집해야 할 데이터, 다음 5장 재검증 순서를 표로 작성해줘.
결론은 가격 확정이 아니라 통과·중단·재측정 기준으로 제시해줘.
```

</details>

> **확인 포인트**
>
> 후속 결과에서는 세그먼트 비중·구매액·이탈률 중 어느 값이 관측인지가 명확하고, 5장 검증 없이 상품안을 확정하지 않아야 합니다.

### 산출물과 검수 기준

- 산출물은 포지셔닝 표, 지표 정의서, 충전·소비 흐름, 사용자군별 영향 표입니다.
- DAU/MAU, 결제율, ARPPU, ARPU, LTV, CPA 등을 동일한 모집단·기간이라고 가정하지 않습니다.
- 서로 다른 통화·환불·중복 결제 처리 기준을 더하지 않았는지 확인합니다.
- “결제자 평균이 상승했다”만으로 성장 경험이나 공정성이 개선됐다고 결론내리지 않습니다.
- `ARPU=PR×ARPPU`는 같은 기간·같은 활성 모집단과 결제액 정의에서 검산합니다. PR은 백분율 표시를 소수로 바꿔 사용합니다.
- 책의 단순 LTV 근사는 `ARPU/주기 이탈률`입니다. ARPU와 이탈률의 관측 주기를 맞추고 일정하다는 가정을 적습니다. 이탈률 0에서는 식이 정의되지 않으며, 원문의 표현 불일치는 [원문 페이지 지도](../.agents/skills/game-balance-bible/references/source-map.md)에 기록되어 있습니다.
- 책의 사례 수치나 결제 방식은 현재 시장의 기준으로 단정하지 않습니다.
- 표6.1의 손익분기월 산식은 원문에 없습니다. 실제 회수 시점은 코호트별 누적 수익·비용으로 계산하고, 본문과 상품표의 가격·구매 목록을 섞어 합산하지 않습니다.

### 다른 장과 잇기

4장의 가치 체계와 소비 모델이 수익화의 사용처를 만들고, 5장은 사용자군별 실제 성장·전투 결과를 확인합니다. 7장은 상품·보상 시점이 리듬을 깨는지 보여주며, 8장은 수익화 검증 모델의 입력·출력을 다른 모델과 연결합니다.

## 7장 — 수치 시각화: 그래프를 결론이 아니라 경험 가설로 쓰기

### 사용할 상황

- 특정 구간이 지루하거나 급격하게 어려워진다는 피드백을 시간축에서 살필 때
- 성장 해금, 보상, 전투 시간, 소비, 수익화의 시점을 조정할 때
- 긴 표를 보고도 콘텐츠 공백과 목표 과밀을 발견하기 어려울 때

### 준비할 입력

- 레벨·일차·세션 등의 공통 가로축과 콘텐츠·성장·보상·전투 데이터
- 단일 피해, 전투 시간, 성장의 질적·양적 변화, 해금·의례·보상 시점
- 어떤 사용자군의 어느 구간을 보고 있는지와 플레이 테스트 또는 로그 근거

### 사용 전략

1. 목표 시간을 레벨·일차·세션 중 하나로 고정하고 다른 데이터를 같은 축에 정렬합니다.
2. 성장의 양적 증가와 질적 변화, 전투의 단일 피해와 전투 시간을 다른 행 또는 그래프로 둡니다.
3. 단계 목표는 단계 구분 → 해금 기능 검증 → 성장 리듬 검증 → 과금 깊이 검증 → 유저 목표 설정으로 구성합니다. 단계마다 시간·레벨·새 기능·소비량·목표를 한 행에 놓습니다.
4. 저점·과밀·급상승을 찾으면 보상값만 올리지 말고 해금, 소비, 난이도, 전투 시간을 원 모델에서 추적합니다.
5. 시간 변화는 꺾은선, 주기별 구성 비교는 막대, 한 시점의 전체 대비 비중은 원그래프로 구분합니다. 다른 단위는 별도 축·패널로 표시합니다.
6. 그래프의 가중치·흥미도는 가설로 표시하고 사용자군별 플레이 테스트·검증 데이터로 교차 확인합니다.

### 가정 예시: 리듬 공백 찾기

가정 예시로 0~60분의 세션 표에 전투 스킬 해금, 장비 강화, 동료 해금, 희귀 보상 시점을 기록할 수 있습니다. 20~30분 사이에 질적 변화와 짧은 목표가 모두 없다는 사실은 점검 가설입니다. 그 공백을 새 보상으로 메울지, 전투 시간이나 강화 비용을 바꿀지는 3·4·5장의 계산을 다시 한 뒤 결정합니다.

### 기본 요청 프롬프트

```text
$game-balance-bible
[레벨/일차/세션] 축에서 성장·보상·전투·소비 리듬을 검토해줘.
각 시점 데이터와 사용자군은 [입력]이다.
7장의 리듬감·의례감·몰입감·단계 목표 관점으로 표와 그래프 설계안을 제시해줘.
관찰 사실, 해석 가설, 3~6장에서 재계산할 변경 후보를 구분하고
한 지표의 매끄러움만으로 결론내리지 않는 검수 항목도 넣어줘.
```

### 고급 프롬프트 사용 예시

7장은 차트를 결과물로 끝내지 않고, 리듬·의례·몰입·단계 목표라는 경험 가설을 검증하는 도구로 씁니다. 아래 시간·점수·수량은 **가정 예시**이며, 흥미도 점수는 관측 사실이 아니라 팀이 검증할 가설로 다룹니다.

공통 검수에서는 시간축의 원점, 세션·계정·이용자 중 집계 단위, 누적과 구간값, 결측·중도 이탈의 처리법을 붙입니다. 그래프의 모양만으로 원인을 확정하지 않고, 대응하는 전투·경제·검증 모델의 원자료까지 되돌아갑니다.

단계 목표 표의 해금은 기능 사용 가능 시점이며 실제 사용·만족을 뜻하지 않습니다. 둘을 검증하려면 행동 로그나 플레이 테스트가 추가로 필요합니다.

#### A. 첫 60분의 질적·양적 성장 리듬 설계

튜토리얼 이후 보상이 몰리거나 비는 구간을, 기능 해금과 수량 보상을 같은 시간축에서 검토할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
7장 리듬감 관점으로 첫 60분 경험 가정안을 검토해줘.
양적 보상은 10분에 레벨업, 25분에 장비 강화, 45분에 레벨업이며 각 보상은 1회다.

의례 연출은 보상량 증가와 분리하고, 확인할 플레이 테스트 질문도 적어줘.
책의 리듬감 원리와 이 타임라인 가정을 구분하며 단위·반올림·성공 기준을 명시해줘.
```

<a id="ch07-b"></a>

#### B. 30일 단계 목표와 해금·소비를 연결하는 설계표

레벨 표만으로는 보이지 않는 콘텐츠 갱신, 성장 목표, 수익화 깊이의 관계를 한 표에서 검토할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
7장 단계 목표 5단계로 30일 가정 데이터를 설계해줘.
구간은 1~3일 튜토리얼, 4~10일 초보, 11~20일 성장, 21~30일 정체로 나눈다.
해금은 각 구간에 스킬, 장비 강화, 협동 던전, 상위 도전을 차례로 하나씩 배치한다.
가정상 각 구간 마지막 날의 게임 시작 후 누적 성장 재화 소비는 100, 300, 700, 1,200이다.
단위는 재화/활성 이용자 1명이고, 각 구간 동안의 순증 비용을 따로 계산해줘.
각 단계에 시간·레벨 범위(미정이면 빈칸)·기능·중복 콘텐츠·흥미도 가설·성장 목표·소비·유저 목표를 표로 만들어줘.
과금 깊이는 소비량 자체가 아니라 별도 가치 체계가 있어야 계산 가능하다고 표시해줘.
단계 길이와 콘텐츠 신선도를 검증할 실제 행동·이탈 데이터 요구사항을 적어줘.
책의 단계 목표 절차, 프로젝트 가정, 다음 5·6장으로 넘길 검증 항목을 구분해줘.
```

</details>

> **확인 포인트**
>
> 구간 순증 비용은 `100·200·400·500`, 30일 총소비는 `1,200`인지 확인합니다. 기말 누계를 더해 중복 집계하거나, 가치 체계 없이 금액·매출을 산출하지 않습니다.

<a id="ch07-c"></a>

#### C. 질문별 그래프 선택과 동일 기준 비교

하나의 화려한 차트로 모든 문제를 설명하지 않고, 비교 대상과 시간축에 맞는 시각화 명세를 만들 때 씁니다.

<details>

- 전투 리듬의 이중축은 피해와 시간 단위를 각각 유지합니다. 몰입 점수는 척도·출처·합산 규칙을 밝혀야 재현할 수 있습니다.

### 다른 장과 잇기

## 8장 — 수치 모듈화: 변경 가능한 모델과 영향 범위 만들기

### 사용할 상황

- 장비·캐릭터·드롭·이벤트 같은 기능이 늘어나며 표와 공식의 출처가 불명확해질 때
- 비용 하나를 고쳤을 때 생산·성장·전투·수익화 중 어디를 재검증해야 하는지 정할 때
- 검증된 구조를 다음 콘텐츠나 프로젝트에 재사용하려 할 때

### 준비할 입력

- 현재 수치 모델 목록, 각 모델의 책임·입력·출력·상태·인터페이스·계산 로직
- 매개변수 원천, 다른 모델에서 호출하는 데이터, 갱신 주기와 소유자
- 변경 요청, 영향 받을 사용자 경험, 기존 검증 결과와 재검증 가능한 데이터

### 사용 전략

1. 기초 성장, 속성 성장, 성장 모듈 성장, 몬스터 난이도, 성장 소비, 생산, 경제 검증, 성장 검증, 수익화 검증, 전투 기본 모델의 10개 모델에 현재 자료를 배치합니다. 번호는 일방향 실행 순서가 아니며, 전투 기본 모델은 필요한 설계·검증 단계에서 호출합니다.
2. 각 모델에 매개변수 정의 → 데이터 호출 → 모델 계산을 작성하고, 원천 데이터와 파생 데이터를 구분합니다.
3. 입력·출력·단위·주기·상한·반올림·소유자를 계약으로 적습니다.
4. 변경한 모델에서 나가는 출력과 그 출력을 읽는 다음 모델을 따라가 재검증 목록을 만듭니다.
5. 재사용할 때는 숫자를 복사하지 않고 경험 목표, 인터페이스, 제약, 검증 순서를 함께 이식합니다.

[원문 성유물 예시](../.agents/skills/game-balance-bible/chapters/ch08-modularization.md#원문-성유물-예시-재현-가능한-입력과-계산)를 학습할 때는 출현 횟수·별 등급 비율·초기값·돌파 횟수를 입력으로 구분합니다. 현재 게임 규칙으로 간주하지 않으며, 원문에 없는 부속성 선택 가중치·변동 후 반올림은 확정값으로 채우지 않습니다.

### 가정 예시: 모델 계약

가정 예시로 `공격력 = 초깃값 + (레벨-1)×레벨 증폭값`이라는 성장 모델을 두면, 입력은 레벨과 두 매개변수, 출력은 공격력입니다. 초깃값 100과 증폭값 50을 가정하면 레벨 10의 출력은 `100+(10-1)×50=550`입니다. 이 수치는 설명용이며, 실제 모델에는 레벨 범위·직업 보정·버프 적용 시점과 다른 모델이 읽는 공격력의 단위를 계약에 추가해야 합니다.

### 기본 요청 프롬프트

```text
$game-balance-bible
[변경 요청] 때문에 수치 모델을 정리하고 영향 범위를 확인하려고 한다.
현재 모델·입력·출력·매개변수·데이터 원천·갱신 주기는 [입력]이다.
8장의 10개 모델 연결망에 배치하고, 각 모델의 계약을 표로 작성해줘.
전투 기본 모델을 마지막에만 실행하는 순서로 고정하지 마.
매개변수 정의→데이터 호출→모델 계산을 분리하며,
변경 후 재검증할 경제·성장·전투·수익화 모델과 테스트 순서를 제시해줘.
```

검증 결과도 모델 계약의 출력으로 버전과 함께 보관합니다.

#### B. 매개변수·호출값·계산식의 수식 계보 추적

단순 성장식이라도 값의 출처를 추적해, 임의 상수와 다른 모델에서 넘어온 데이터를 구별할 때 씁니다.

<details>

```text
$game-balance-bible
8장의 매개변수 정의→데이터 호출→모델 계산으로 장비 공격력 모델을 작성해줘.
가정 매개변수는 공격력 초깃값 100, 레벨 증폭 50, 레벨 10이며 단위는 공격력 점과 레벨이다.
기본 식은 공격력=초깃값+(레벨−1)×레벨 증폭으로 고정한다.
장비 모듈은 호출값인 전체 속성 성장 550의 20%를 배분받는다는 별도 가정을 둔다.
기본 식 결과와 배분값 550×0.20을 각각 계산하고, 둘을 자동 합산해도 되는지 계약 없이는 판단하지 마.
각 값에 정의 위치, 호출 원본, 계산 단계, 반올림, 상한, 다음 모델 전달값을 붙여줘.
책의 구축 3단계와 이 수치 예시를 구분하고, 단위 불일치·순환 호출·상수 하드코딩 검사도 넣어줘.
산출물은 수식 계보 표, 계산 검산, 계약 위반 사례, 성공 기준 순서로 작성해줘.
```

</details>

> **확인 포인트**
>
> 기본 식은 `550`, 배분 호출값은 `110`인지와 둘을 같은 의미의 공격력으로 중복 합산하지 않는지 확인합니다.

<a id="ch08-c"></a>

#### C. 소비 비용 변경의 영향 범위와 검증 순서

한 모듈의 숫자만 바꿨을 때 성장·경제·수익화·전투에 다시 확인할 순서를 정할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
장비 강화 1단계 비용을 가정상 40에서 50 재화로 바꾸는 변경 영향 분석을 해줘.
변경 대상은 5단계 성장 소비 모델이며, 생산량·성장 속성·상품 지급·몬스터 표는 아직 변경하지 않았다.
재화 단위는 재화/강화 1단계, 기간·사용자군·초기 재고는 실제 데이터가 없어 미정이다.
8장의 의존 순서에 따라 직접 영향, 간접 영향, 영향 없음(가정상)을 구분해줘.
먼저 재계산할 모델과 그 다음 검증 모델을 번호와 이유로 제시해줘.
모델 7(경제 검증)의 잔여, 모델 8(성장 검증)의 실제 성장,
모델 9(수익화 검증), 모델 10(전투 기본)의 결과에서 필요한 입력과 통과 기준을 적어줘.
40→50의 증가율을 소수점 첫째 자리 %로 계산하고, 재화 부족을 곧바로 결제 압박으로 해석하지 마.
책의 연결 원리, 변경값, 미정 데이터, 추가 제안을 분리한 변경 명세서로 작성해줘.
```

</details>

> **확인 포인트**
>
> 증가율 `25.0%`인지와 생산·소비·성장 검증을 거치지 않고 수익화나 전투 결과를 단정하지 않는지 확인합니다.

<a id="ch08-d"></a>

#### D. 검증 가능한 재사용 모델 계약 만들기

다음 콘텐츠에서도 같은 시스템을 쓰되 숫자를 복사하지 않고, 인터페이스와 테스트를 계승할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
가상 던전 보상 모듈을 다른 콘텐츠에 재사용하기 위한 모델 계약을 작성해줘.
입력은 난이도 등급 1~3, 고정 보상 20/40/60 재화, 랜덤 보상 확률과 수량은 아직 미정이다.
출력은 재화/플레이, 재화/일, 소비 모델 전달값이며 참여 횟수·사용자군·기간도 미정이다.
8장의 기능·상태·인터페이스·로직을 구분하고, 매개변수 정의·데이터 호출·모델 계산을 각각 적어줘.
고정 생산과 랜덤 생산을 구분하되 랜덤 확률을 임의로 채우지 말고 필요한 계약 필드로 남겨줘.
재사용 금지 조건, 버전 관리 항목, 단위·반올림·상한, 입력 검증, 경제·성장·전투 회귀 테스트를 제시해줘.
책의 모듈 재사용 원리와 이 던전 데이터가 가정이라는 점을 분리하고, 성공 기준을 재현 가능성으로 정의해줘.
산출물은 계약 표, 의존 관계, 테스트 명세, 변경 이력 템플릿 순서로 작성해줘.
```

</details>

> **확인 포인트**
>
> 등급별 고정 보상 `20/40/60`이 랜덤 보상의 기대값으로 바뀌지 않고, 미정 확률을 수치로 꾸며내지 않는지 확인합니다.

<a id="ch08-followup"></a>

#### 결과를 이어서 개선하는 후속 프롬프트

앞선 책임 맵·계보·영향 분석·계약 중 하나를 실제 변경에 적용해, 입력 변경부터 회귀 결과까지 추적할 때 사용합니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
바로 앞 8장 산출물을 기준선으로 사용해 변경 1건의 추적 표를 만들어줘.
실제 데이터, 가정 매개변수, 다른 모델에서 호출한 값을 세 열로 분리해줘.
변경 전후 값·단위·반올림·상한·버전, 직접 출력, 영향받는 10단계 모델을 기록해줘.
매개변수 정의→데이터 호출→모델 계산 순서에서 어느 단계가 달라졌는지와 수식 계보를 보여줘.
소비·생산·경제 검증·성장 검증·수익화·전투 중 실제 영향받는 모델을 골라 재검증 순서와 피드백을 제안해줘.
미정 입력은 결과값으로 추측하지 말고, 회귀 테스트의 보류 조건으로 남겨줘.
책 근거와 프로젝트 계약·가정을 구분하고, 통과·실패·되돌림 기준을 표로 작성해줘.
결론은 숫자 승인 대신 다음 모델에 전달할 검증된 출력 목록으로 제시해줘.
```

</details>

> **확인 포인트**
>
> 후속 결과에는 한 변경이 어느 계약 필드를 바꾸고 어떤 회귀를 통과해야 재사용 가능한지 남아 있어야 합니다.

### 산출물과 검수 기준

- 산출물은 10단계 맵, 모델 계약 표, 데이터 계보, 변경 영향·재검증 목록입니다.
- 한 모델의 입력이 다른 모델에서 중복 정의되지 않고 원천이 명시됐는지 확인합니다.
- 비용 변경 뒤 생산·경제 검증만이 아니라 성장·전투·수익화 영향을 포함했는지 확인합니다.
- 독립성을 고립으로 오해해 연결 모델의 재검증을 빼지 않았는지 확인합니다.
- 모델 계약에 단위·기간·상한·반올림·사용자군 조건이 빠지지 않았는지 확인합니다.

### 다른 장과 잇기

8장은 1장의 5단계 프로세스를 구현 구조로 바꿉니다. 3~6장의 모델을 각각 10단계 체계에 연결하고, 7장에서 발견한 경험 문제를 특정 모델·입력·출력으로 되돌립니다. 변경 후에는 [검수와 테스트 가이드](validation.md)의 원문 대조·독립 계산·호스트 사용 시험을 적용합니다.

## 장을 연결하는 실무 흐름 3가지

### 1. 신규 콘텐츠의 전투·보상 설계

1. 2장에서 목표 경험과 사용자·콘텐츠 구간을 정합니다.
2. 3장에서 목표 전투 시간, 속성, 대미지·확률 플로, NPC 템플릿을 만듭니다.
3. 4장에서 성장 비용과 보상·드롭 I/O를 같은 주기로 연결합니다.
4. 5장에서 실제 도달 속성과 전투 결과를 사용자군별로 검증합니다.
5. 7장에서 보상·해금·전투 시간의 시간축을 읽고, 8장 계약에 변경 이력을 남깁니다.

#### 통합 요청 예시

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
신규 던전의 전투·보상·성장 구조를 연결해 검토해줘.
장르·사용자·구간·목표 전투 시간·목표 성장 주기: [입력]
플레이어/몬스터 속성·전투 판정: [표 또는 파일]
성장 단계·비용·입장 제한·고정/랜덤 보상: [표 또는 파일]
2→3→4→5→7→8장 순서로 필요한 내용을 읽고 단계별 결과를 전달해줘.
목표 경험, 전투 플로, 비용·보상 I/O, 도달 속성과 전투 결과,
시간축의 목표·보상 배치, 모델 계약을 각각 표로 만들어줘.
단위와 주기는 고정하고, 계획 소비와 실제 지출을 구분해줘.
모든 단계를 한 번에 확정하지 말고 누락된 입력과 검증해야 할 가정을 표시해줘.
마지막에 최소 변경안, 영향받는 모델, 통과 기준과 테스트 항목을 정리해줘.
```

</details>

### 2. 재화 부족 또는 누적 문제 조사

1. 1장에서 문제 재화가 어느 성장·플레이·수익화 루프에 속하는지 표시합니다.
2. 4장에서 모든 생산·소비·거래·이벤트를 I/O에 넣고, 가치 기준을 고정합니다.
3. 5장에서 같은 기간의 누적 생산·소비·잔여와 공유 지갑 제약을 계산합니다.
4. 3장에서 변경이 필요한 성장 속성·난이도 영향이 있는지, 7장에서 체감 공백이 생기는지 확인합니다.
5. 8장에서 생산·소비·검증 모델의 입력 변경과 재검증 범위를 고정합니다.

#### 통합 요청 예시

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
[재화 이름]이 [구간]에서 [부족/누적]되는 원인을 조사해줘.
동일 기간·동일 사용자군의 초기 재고·유입·실제 지출: [입력]
계획 성장 비용·소비 우선순위·이벤트·환전·거래 조건: [입력]
성장/전투 결과와 문제 발생 시점: [관찰 자료]
1→4→5장에서 구조, 생산·소비 합계, 잔여량·비율과 실제 잔고를 따로 확인해줘.
누락된 생산, 중복 집계, 단위 오류, 공유 재화 배분, 소비 상한을 점검해줘.
3·7장에서 성장·전투·리듬에 미치는 영향이 있는지 확인해줘.
관찰된 사실과 원인 가설을 분리하고, 반증할 자료나 실험을 제시해줘.
수정 후보마다 공급/소비/참여율 중 바뀌는 변수와 장단점을 비교해줘.
8장의 연결 모델에 맞춰 재검증 순서를 정리해줘.
```

</details>

### 3. 수익화 변경의 영향 검증

1. 6장에서 상품이 경험·성장·기능·화폐 중 무엇을 바꾸는지와 지표의 기간·모집단을 정의합니다.
2. 4장에서 지급물과 소비처가 경제 총량·가치 체계에 더하는 변화를 계산합니다.
3. 5장에서 무료·결제 사용자군의 도달 레벨, 잔여 재화, 전투 결과를 같은 기간으로 비교합니다.
4. 7장에서 상품·보상 시점이 핵심 루프의 리듬과 단계 목표를 과도하게 앞당기거나 막는지 읽습니다.
5. 8장에서 충전·소비·경제·성장·전투 모델을 다시 실행할 변경 목록으로 기록합니다.

#### 통합 요청 예시

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
[상품 변경]이 결제와 플레이 경험에 미치는 영향을 검토해줘.
상품 가격·지급물·구매 횟수·소비처·기간·대상 조건: [변경 전후 입력]
활성/결제 사용자 정의·기간·매출·환불·사용자군 비중: [입력]
사용자군별 초기 재고·생산·소비·경험치·전투 데이터: [입력]
6장에서 결제 유형, 이벤트 목적, 충전과 게임 내 소비를 구분해줘.
4→5장에서 가치 체계, 경제 총량, 도달 성장과 전투 격차를 계산해줘.
7장에서 목표·보상 시점과 진행 막힘을 비교하고, 8장에서 변경 영향을 추적해줘.
KPI 계산은 모집단·기간·통화를 맞추고, 기대 예측과 관측 결과를 구분해줘.
매출 증가만으로 개선을 확정하지 말고 진행 가능성·격차·리듬을 함께 판단해줘.
변경 전후 검산표, 민감한 가정, 통과 기준, 검증이 끝나지 않은 항목을 남겨줘.
```

</details>

## 결과를 다음 단계에 넘기기 전 확인할 것

| 확인할 항목 | 결과에 남아 있어야 할 근거 |
|---|---|
| 출처 | 사용한 장·참고 파일과 프로젝트 데이터, 새 가정의 구분 |
| 계산 | 변수·단위·기간·모집단·중간식·반올림과 핵심 합계 |
| 범위 | 입력이 빠져 계산하지 못한 항목, 식의 적용 조건과 경계값 |

| 검증 | 독립 검산 또는 실험 결과, 통과·실패 기준과 남은 플레이 검증 |
