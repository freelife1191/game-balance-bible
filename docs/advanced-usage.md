# 장별 고급 활용법

<a id="document-top"></a>

[가이드 홈](index.md) · [README](../README.md) · [릴리스 안내](../release/README.md) · [검수와 테스트](validation.md) · [프로젝트 사례](project-example.md)

이 문서는 포함된 `game-balance-bible` 스킬을 책의 8개 장에 따라 실무 설계·학습·장별 참고에 사용하는 방법을 정리합니다. 장별 기본 요청 8개에 더해 **공통 고급 예시 4개, 장별 고급 예시 32개와 보완 예시 1개, 장별 후속 요청 8개, 장 연결 통합 요청 3개**를 제공합니다. 여러 요청 앞에 보낼 공통 맥락 요청과 실행 검산 요청도 하나씩 둡니다. 필요한 상황을 골라 입력값을 바꾸고 결과를 다음 요청으로 이어갑니다. Codex에서는 `$game-balance-bible`, Claude Code와 Antigravity에서는 `/game-balance-bible`로 시작합니다. 아래 프롬프트의 `$`는 Codex 표기이므로 다른 호스트에서는 `/`로 바꿉니다.

> [!IMPORTANT]
> **원문 근거와 합성 예시**
>
> 책에서 정리한 개념·공식과 여기서 제안하는 작업 순서는 구분합니다. **`가정 예시`**라고 표시한 숫자와 상황은 이 가이드를 위한 새 예시이며 책의 사례가 아닙니다. 실제 프로젝트 값, 기간, 유저군, 난수 규칙을 제공하고 결과를 별도로 검증해야 합니다. 이 가이드는 책의 모든 이미지·표를 완전하게 보존하지도, 현재 서비스의 정답을 보장하지도 않습니다.

## 사용 전에 정할 공통 입력

스킬에 숫자만 던지기보다 다음 정보를 함께 줍니다. 값이 없으면 스킬이 빈칸을 가정으로 명시하게 요청합니다.

1. **장르·목표 경험** — 장르, 목표 경험, 대상 유저와 콘텐츠 구간을 적습니다.
2. **단위** — 단위를 고정합니다. 예를 들어 피해는 `1회 실제 피해`, DPS는 `초당 피해`, 비용은 `자원/단계`, 생산은 `자원/일`처럼 씁니다.
3. **기간·모집단** — 기간과 모집단을 고정합니다. 일일 누적값과 시즌 누적값, 전체 유저와 과금 유저 지표를 같은 열에 섞지 않습니다.
4. **계산 규칙** — 난수·반올림·초깃값·상한을 적습니다. 순차 판정인지, 결과 칸이 100%를 나눠 갖는지, 첫 타격 시점이 언제인지가 결과를 바꿉니다.
5. **산출물** — 원하는 산출물 형태를 지정합니다. 표, 계산식, 변경안, 테스트 케이스, 장별 학습 노트 가운데 필요한 것을 말합니다.

각 장의 답변에는 가능한 한 **입력과 가정 → 계산·판단 → 조정안 → 검수 기준 → 다음 장 영향** 순서를 요구합니다. 읽을 자료는 [질문별 자료 지도](../.agents/skills/game-balance-bible/references/task-map.md)에서 찾습니다. 원문 근거가 필요한 수식·표는 [원문 페이지 지도](../.agents/skills/game-balance-bible/references/source-map.md)를 함께 확인합니다.

## 프롬프트를 고르고 결과를 이어가는 방법

1. **상황을 고릅니다.** 각 장의 기본 요청은 전체 구조를 잡고, A~D 예시(4장은 보완 예시 E 포함)는 특정 문제를 깊게 다룹니다. 새 기획은 1·2장, 전투는 3장, 보상·비용은 4장, 계산 검수는 5장부터 시작합니다. 자료 선택이나 산출물 검토처럼 장을 가리지 않는 작업은 [장을 가리지 않는 공통 고급 예시](#common-examples)에서 고릅니다.
2. **입력값을 바꿉니다.** `[입력]`은 실제 표·로그·메모로 채웁니다. `가정 예시`는 그대로 연습할 수 있으며, 실무에서는 게임의 값과 규칙으로 바꿉니다. 파일 경로를 쓰면 현재 에이전트가 접근할 수 있는 실제 경로를 제공합니다.
3. **결과를 확인합니다.** 예시 아래의 `확인 포인트`로 산식·합계·조건·누락을 점검합니다. 계산값이 맞아도 체감 밸런스는 별도 플레이 검증으로 확인합니다.
4. **후속 요청을 사용합니다.** 각 장의 후속 요청은 제목과 소개 문장에 적힌 선행 예시 하나를 이어받습니다. 같은 대화에서는 방금 나온 표·계산을 고쳐 비교합니다. 새 대화에서는 프로젝트 맥락과 함께 후속 요청의 인계 항목(선행 결과·선택안, 유지할 확정 조건과 미정 사항, 이어받을 조건의 판정·근거·미확인 항목)을 직접 채워 보냅니다. 판정은 성립·불성립·미확인·해당 없음 가운데 하나로 적고, 근거가 원문 위치·입력·관측 중 무엇인지 밝힙니다. 이 네 상태는 조건을 적용할지 판단하는 표기이며 검수 결과의 통과·실패를 뜻하지 않습니다.
5. **다음 장에 전달합니다.** 예를 들어 3장의 성장 속성을 4장의 비용·보상에 연결하고, 5장에서 실제 도달 속성과 전투 결과를 검증합니다. [장을 연결하는 실무 흐름 세 가지](#integrated-workflows)에 통합 요청도 있습니다.

### 여러 요청에서 재사용할 프로젝트 맥락

아래를 먼저 보내고 필요한 장의 요청을 이어 붙입니다. 목적이 단일 용어 설명이면 필요한 항목만 적습니다.

```text
$game-balance-bible
앞으로 다음 프로젝트 맥락으로 설계와 검수를 진행해줘.
장르·테마: [입력]
대상 유저·세그먼트: [입력]
목표 경험·판정 기준: [입력]
콘텐츠 구간·관측 기간·시간 단위: [입력]
전투·성장·경제의 현재 데이터 또는 접근 가능한 파일: [입력]
고정할 규칙과 바꿀 수 있는 매개변수: [입력]
반올림·초깃값·상한·확률 판정·첫 타격 시점: [해당 항목 입력]
답변은 책의 근거 / 프로젝트 데이터 / 가정 / 추가 제안을 구분해줘.
주제에 필요한 장과 참고 파일만 읽고, 사용한 파일·섹션을 밝혀줘.
원문 쪽수는 근거 파일에서 확인되는 범위만 적어줘.
없는 핵심 데이터는 무엇인지 밝히고, 가정으로 계산한 값은 확정값과 구분해줘.
```

### 원하는 깊이와 산출물을 지정하는 문장

| 목적 | 각 프롬프트 끝에 덧붙일 요청 |
|---|---|
| 학습 | ‘개념→작은 계산→오답 원인 순서로 설명하고, 연습문제와 해설을 별도 항목으로 만들어줘.’ |
| 설계 | ‘변경 가능한 매개변수와 고정 조건을 구분하고, 최소 변경안과 대안의 차이를 비교해줘.’ |
| 계산 구현 | ‘입력·중간식·단위·반올림을 표로 적고, 필요하면 의존성 없는 검산 코드를 제공해줘.’ |
| 시뮬레이션 | ‘확정 계산과 난수 실험을 구분하고, 난수 시드·횟수·모형 가정·오차 범위를 기록해줘.’ |
| 장별 참고 | ‘해당 장·공식 참고·용어집에서 근거를 찾아 설명하고, 확인되지 않는 원문 내용은 분리해줘.’ |
| 수정 검수 | ‘변경 전후 차이와 영향받는 장을 정리하고, 통과 기준·실패 조건·미확인 항목을 남겨줘.’ |

### 계산 결과를 실행 증거로 확인하기

숫자가 맞는 것과 계산 도구를 실제 실행한 것은 별도 확인 사항입니다. 검산이 필요하면 다음 요청을 계산 입력과 함께 사용합니다.

```text
$game-balance-bible
앞선 계산의 핵심 수치를 Python 또는 사용 가능한 계산 도구로 실제 실행해 독립 검산해줘.
입력·핵심 식·실행 방법·실행 결과·판정을 보여줘.
실행하지 못하면 미실행이라고 적고, 추론한 계산값을 실행 결과로 표현하지 마.
```

응답의 ‘검산했다’는 문장만으로 완료를 판단하지 않고 도구 호출·출력·오류와 최종 값을 함께 확인합니다. 일부 예시의 실제 실행과 관측 한계는 [프롬프트 표본 검증](validation.md#prompt-samples)에 기록합니다.

이 구분은 스킬의 [실행 검산 절차](../.agents/skills/game-balance-bible/patterns.md#계산-실행-검산--실무-보완)에도 반영했습니다. 공유 재화·단계 조회를 검산할 때는 비용 제약을 만족하는 목록과 잔여량부터 확인하고, 조합 개수만으로 정확성을 판정하지 않습니다. 실행 오류를 수정했다면 재실행 출력으로 최종 상태를 판단합니다.

<a id="common-a"></a>

### 공통 A. 질문에 맞는 장·참고 자료를 고르고 근거 범위 밝히기

질문 하나가 여러 장에 걸칠 때, 계산하기 전에 어떤 자료를 왜 읽는지와 원문 위치를 어떻게 인용할지 먼저 정합니다.

| 항목 | 내용 |
|---|---|
| 입력 | 질문 1개와 가정 상자 풀: 강화석 4~8개 가중치 50(변경안 40), 코인 100개 가중치 30, 꽝 가중치 20, 하루 1회 개봉 |
| 원하는 산출물 | 읽을 장·참고 파일·절의 순서와 이유, 제외할 장과 이유, 출처 표시 규칙, 원문 대조가 필요한 위치 목록 |
| 미정 사항 | 장비 비용 곡선, PvP 피해식, 유저군 |
| 기대 결과 | [질문별 자료 지도](../.agents/skills/game-balance-bible/references/task-map.md)의 행으로 자료를 고르고, 고른 절은 전체를 읽으며, 원문 PDF를 찾아 열지 않음 |

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
아래 질문에 답하기 전에 읽을 자료부터 골라줘. 아직 계산은 하지 마.
질문(가정): 던전 보상 상자의 강화석 가중치를 50에서 40으로 낮추면 30일 장비 완성 시점과 같은 레벨 PvP 결과가 어떻게 달라지나?
가정 입력: 상자 풀은 강화석 4~8개 가중치 50, 코인 100개 가중치 30, 꽝 가중치 20이고 하루 1회 연다.
미정 사항: 장비 비용 곡선, PvP 피해식, 유저군은 아직 정하지 않았다.
질문별 자료 지도에서 해당 행을 찾고, 읽을 장·참고 파일·절을 순서와 이유와 함께 표로 적어줘.
고른 파일은 검색 결과 몇 줄이 아니라 해당 절 전체를 읽는다는 전제로, 읽을 범위를 절 이름까지 밝혀줘.
이 질문에 필요 없는 장과 그 이유도 적어줘.
답변에서 (인쇄 N / PDF M) 위치가 붙은 책의 서술, 스킬 정리, 내 가정을 어떻게 구분해 표시할지 정해줘.
원문 PDF는 찾아 열지 말고, 원문과 대조할 항목은 자료에 적힌 위치만 목록으로 남겨줘.
미정 사항 때문에 아직 답할 수 없는 부분과 먼저 받아야 할 입력을 구분해줘.
```

</details>

> **확인 포인트**
>
> 자료 지도의 `상자 가중치·드롭 평균·기대가치`, `레벨 검증·VLOOKUP·공유 재화·성장 검증`, `PvE·PvP·과금군·란체스터` 행을 근거로 4장과 경제 모델 참고의 랜덤 드롭 절, 5장의 경제·성장·전투 검증 절, 전투 공식 참고를 고르는지 확인합니다. 질문과 관계없는 장은 이유와 함께 빠져야 합니다. 위치가 붙지 않은 문장을 책의 서술로 단정하지 않는지, PvP 피해식이 미정이라 PvP 결과의 결론을 보류하는지도 봅니다.

<a id="common-b"></a>

### 공통 B. 같은 총비용·기간에서 균등 비용안과 구간 비용안 비교하기

총비용·공급·기간을 같게 고정한 두 비용안의 리듬 차이를 비교하고, 책의 선택 기준이 이 입력만으로 판단 가능한지 가립니다.

| 항목 | 내용 |
|---|---|
| 입력 | 장비 강화 20단계, 총비용 강화석 2,000개, 일반 유저 일일 반복 공급 40개, 시작 재고 0, 다른 공급·소비 없음. 1안은 단계마다 100개, 2안은 1~10단계 60개·11~20단계 140개 |
| 원하는 산출물 | 두 안의 누적 비용·도달일 표, 단계 간격 비교, 책 기준별 판정표, 결정을 바꿀 추가 입력 |
| 미정 사항 | 장비 강화 모듈의 중요도, 단계별 속성 수익, 유저군 참여율 |
| 기대 결과 | 같은 조건에서만 비교하고, 미정 입력이 남으면 어느 안이 낫다고 확정하지 않음 |

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
같은 조건에서 장비 강화 비용 두 안을 비교해줘.
공통 가정: 강화 20단계, 총비용 강화석 2,000개, 일반 유저 일일 반복 공급 40개, 시작 재고 0, 다른 공급·소비는 없다.
1안은 모든 단계가 100개, 2안은 1~10단계 60개·11~20단계 140개다.
두 안의 총비용이 같은지 먼저 검산하고, 단계별 누적 비용과 도달일을 표로 계산해줘.
도달일은 누적 공급이 누적 비용 이상이 되는 첫날로 하고, 그날 공급을 받은 뒤 소비한다고 가정해줘.
10단계·20단계 도달일과 구간별 단계 간격을 비교해줘.
2안이 책의 비선형 소비식과 같은 형태인지 먼저 판정한 뒤, 4장의 선형·비선형 소비 선택 기준을 이 입력에 적용해줘.
기준마다 판정(성립·불성립·미확인·해당 없음)과 근거(원문 위치·입력)를 붙여줘.
모듈 중요도·속성 수익·참여율이 미정이므로 어느 안이 낫다고 확정하지 말고, 결정을 바꿀 추가 입력을 적어줘.
책의 기준, 이 비교의 가정, 추가 제안을 구분해줘.
```

</details>

> **확인 포인트**
>
> 총비용은 1안 `100×20=2,000`, 2안 `60×10+140×10=2,000`으로 같습니다. 10단계 도달은 1안 `1,000÷40=25일`, 2안 `600÷40=15일`이고, 20단계는 두 안 모두 `2,000÷40=50일`입니다. 단계 간격은 1안 2.5일, 2안 1.5일에서 3.5일로 바뀝니다. 2안은 구간마다 비용이 고정된 계단형이라 [경제 모델 참고](../.agents/skills/game-balance-bible/references/economy-models.md#1-소비-모델)의 비선형 소비식과 형태가 다르다는 점을 먼저 짚어야 합니다. 저자는 중요도가 낮고 소비량이 많은 성장 모듈에 비선형 소비를 쓴다고 하면서도 이 기준이 절대적이지 않다고 덧붙입니다(인쇄 137–138 / PDF 167–168). 중요도가 미정인 이 입력에서는 해당 판정이 미확인으로 남아야 합니다.

<a id="common-c"></a>

### 공통 C. 일일 공급 변경이 여러 장에 미치는 영향 추적하기

값 하나를 바꿨을 때 다시 계산할 장과 그대로 둘 장을 나누고, 변경 전 판정이 유지되는지 바뀌는지 기록합니다.

| 항목 | 내용 |
|---|---|
| 입력 | 장비 1개 총비용 강화석 1,200개, 목표 30일, 일반 유저 일일 던전 공급 40개를 32개로 줄이는 변경안, 시작 재고 0, 다른 공급 없음 |
| 원하는 산출물 | 장별 직접·간접·영향 없음(가정) 표, 재계산 순서, 변경 전후 판정표 |
| 미정 사항 | 장비 속성 수익, 상품 구성, 단계 목표 표 |
| 기대 결과 | 판정마다 유지·변경의 이유와 근거 종류가 남고, 부족을 곧바로 결제 압박으로 해석하지 않음 |

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
일일 던전 강화석 공급을 40개에서 32개로 줄이는 변경의 영향을 장별로 추적해줘.
공통 가정: 장비 1개 총비용 강화석 1,200개, 목표 완성 30일, 일반 유저, 시작 재고 0, 다른 공급은 없다.
변경 전후의 30일 누적 공급, 잔여량, 소비 기준 잔여 비율, 완성일을 계산해줘. 완성일은 누적 공급이 1,200 이상이 되는 첫날로 한다.
4장 생산 모델을 직접 영향으로 두고, 5장 경제·성장 검증, 3장 도달 속성과 전투 결과, 6장 수익화, 7장 단계 목표, 8장 모델 연결 순서로 영향 여부를 판정해줘.
각 장에 직접 영향·간접 영향·영향 없음(가정)을 표시하고, 판정 근거가 원문·입력·관측 중 무엇인지 적어줘.
장비 속성 수익·상품 구성·단계 목표 표가 없으므로 3·6·7장의 결과는 미확인으로 두고 필요한 입력을 적어줘.
부족한 강화석을 곧바로 결제 압박이나 가격 인상의 근거로 해석하지 마.
변경 전에 성립하던 판정 중 유지되는 것과 바뀌는 것을 표로 나누고 이유를 적어줘.
책의 연결 원리, 이 변경의 가정, 추가 제안을 구분해줘.
```

</details>

> **확인 포인트**
>
> 변경 전은 `40×30=1,200`으로 30일째 완성되고 잔여는 0입니다. 변경 후 30일 누적은 `32×30=960`, 잔여 `-240`, 잔여 비율 `-240÷1,200=-20.0%`이며 완성은 `1,200÷32=37.5`이므로 38일째입니다. 8장의 성장 검증 모델(모델 8)은 경제 검증(모델 7)의 생산 검증 자원 데이터로 계산하므로(인쇄 243 / PDF 273), 5장 재계산 전에 3장의 전투 결과를 확정하지 않는지 확인합니다.

<a id="common-d"></a>

### 공통 D. 여러 산출물의 단위·모집단·출처 표기 일관성 검토하기

여러 사람이 만든 표와 메모를 합치기 전에 단위·유저군·분모와 책에 관한 주장이 서로 맞는지 점검합니다.

| 항목 | 내용 |
|---|---|
| 입력 | 가정 초안 4개: 생산 표, 소비 표, 지표 보고서, 설계 메모 |
| 원하는 산출물 | 불일치 목록(위치·종류·판정·근거·수정안), 고치지 않을 입력 목록, 합치기 전 확인 질문 |
| 미정 사항 | 활성 유저 수, 소비 표의 유저군 |
| 기대 결과 | 입력 숫자는 바꾸지 않고 해석·식·출처 표기만 고치며, 책에 관한 주장은 스킬 자료의 위치로 대조함 |

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
아래 가정 초안 네 개를 합치기 전에 일관성을 검토해줘. 입력 숫자는 고치지 말고 해석과 출처 표기만 판정해줘.
초안 1(생산 표): 강화석 40개/일, 일반 유저, 30일 누계 1,200개.
초안 2(소비 표): 장비 1개 총비용 1,200개, 집중 유저 기준, 목표 30일.
초안 3(지표 보고서): "ARPU = 월 총결제액 15,000 ÷ 월 과금 유저 500 = 30", "책의 기본 지표인 DAU·MAU로 활성 규모를 본다".
초안 4(설계 메모): "책의 성장 곡선 4종은 선형·지수·로그·주기적 곡선이다", "벤치마크 분할도 합이 100%여야 한다".
표 사이의 단위·기간·유저군·분모 불일치를 찾고, 1,200=1,200이 같은 조건의 비교인지 판정해줘.
책에 관한 주장은 스킬 자료의 위치와 대조해 판정하고, 위치를 찾지 못한 주장은 미확인으로 둬줘.
각 항목에 판정(성립·불성립·미확인·해당 없음), 근거(원문 위치·입력·관측), 수정안을 표로 적어줘.
수정안은 원래 입력을 바꾸지 않고 라벨·식·출처 표기를 고치는 방식으로 제안해줘.
초안을 합칠 때 다시 확인할 질문과 아직 없는 데이터를 마지막에 남겨줘.
```

</details>

> **확인 포인트**
>
> 초안 1·2는 유저군이 달라 `1,200=1,200`을 같은 조건의 일치로 볼 수 없습니다. `15,000÷500=30`은 과금 유저를 분모로 쓴 ARPPU이며, ARPU를 구하려면 활성 유저 수가 필요합니다. 책의 기본 지표는 이탈률(CHURN)·활성 유저 결제율(PR)·ARPPU·ARPU·LTV·CPA이고 DAU·MAU는 책에 정의가 없습니다(인쇄 207–209 / PDF 237–239). 곡선 4종의 네 번째는 ‘주기적 곡선’이 아니라 다항식입니다(인쇄 235–236 / PDF 265–266). 합 100%가 필수인 것은 글로벌 분할이며, 벤치마크 분할은 100%가 아니어도 됩니다(인쇄 73–74 / PDF 101–102).

## 1장 — 수치 프로세스화: 변경을 하나의 시스템으로 다루기

### 사용할 상황

- 신규 성장 기능, 보상 이벤트, 난이도 조정을 동시에 검토해야 할 때
- 한 팀은 전투, 다른 팀은 경제를 담당해 변경 원인과 영향 범위가 분리될 때
- ‘보상을 올리면 좋아질 것 같다’처럼 결과만 있고 유저 경험 목표가 불분명할 때

### 준비할 입력

- 변경하려는 기능, 해결하려는 유저 경험 문제, 적용 콘텐츠와 버전 범위
- 준비·전투·경제·검증·수익화의 현재 입력과 산출물
- 기간, 유저군, 성공 판정 지표와 되돌릴 수 있는 변경 단위

### 사용 전략

1. 5단계인 준비 작업 → 전투 수치 → 경제 수치 → 수치 검증 → 수익화에 현재 자료를 놓습니다.
2. 각 단계에 `결정`, `입력`, `산출물`, `검증 지표`, `다음 단계 전달값`을 한 줄씩 적게 합니다.
3. 변경값이 전투 보상·성장 비용·유저 체감 중 무엇을 바꾸는지 화살표로 연결합니다.
4. 전투와 경제를 각각 계산한 뒤 같은 기간·같은 유저 가정으로 5장에서 합쳐 검증합니다.
5. 수익화 요소가 있으면 매출 관련 결과만 보지 않고 핵심 루프의 부담과 진행 가능성까지 다시 확인합니다.

#### A. 신규 프로젝트의 첫 수치 설계 지도

아직 표가 흩어져 있을 때, 목표 경험부터 검증 순서까지 한 장의 의사결정 지도로 만듭니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
신규 협동 PvE RPG의 첫 수치 설계 지도를 만들어줘.
목표 경험은 10분 세션에서 1회 성장 선택, 30일에 장비 1개 완성이다.
가정 입력: 일일 강화석 40개, 장비 총비용 1,200개, 보스 목표 처치 120초다.
유저군은 신규·일반·집중 유저로 나누고, 실제 비율은 아직 미확정이다.
1장의 준비→전투→경제→검증→수익화 5단계에 결정·입력·산출물·검증 지표를 배치해줘.
각 수치를 책 근거, 내가 준 입력, 추가 제안으로 구분해줘.
30일 장비 목표와 일일 공급의 관계를 계산하고 부족·초과 여부를 표시해줘.
전투 120초 목표를 계산하려면 아직 필요한 입력을 목록화해줘.
수익화는 설계 확정이 아니라 영향 확인 항목으로만 다뤄줘.
먼저 만들 표 3개와, 3~5장에서 이어 계산할 순서를 제시해줘.
성공 기준은 목표 주기·유저군·단위가 모든 표에서 일치하는 것이다.
```

</details>

> **확인 포인트**
>
> 결과에서 장비 비용 1,200개를 목표 30일로 나눈 필요 공급이 `1,200 ÷ 30 = 40개/일`이므로, 가정한 일일 공급만으로 해당 장비 하나의 목표 주기에 맞는지 확인합니다.
>
> 책은 수익화를 모든 게임의 최종 목표이자 플레이 리듬을 바꿀 수 있는 양날의 검으로 봅니다(인쇄 6 / PDF 34). 이 예시에서 수익화를 영향 확인 항목으로만 두는 것은 이 가이드가 정한 범위이므로, 결과가 이 범위를 책의 지침처럼 쓰지 않는지도 봅니다.

<a id="ch01-b"></a>

#### B. 기존 수치의 연결 감사

전투·보상·상점 담당 표가 따로 있을 때, 중복 공급과 빠진 소비처를 찾아 변경 전제부터 정리합니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
기존 던전 보상 변경안을 1장의 5단계 연결로 감사해줘.
현재 입력: 일일 던전 강화석 20개, 주간 퀘스트 70개, 이벤트 1회 100개다.
장비 강화는 주당 150개, 스킬 강화는 주당 80개를 같은 강화석으로 소비한다.
던전 보상은 전투 보상 표와 경제 생산 표에 각각 20개로 기록되어 있다.
이벤트 보상은 일회성이고 대상은 신규 유저만이라는 가정이다.
같은 기간을 7일, 같은 유저군을 일반 유저로 고정해 생산·소비 연결 표를 작성해줘.
각 행을 1장 I/O 구조의 생산 칸(플레이 생산·활동 생산)과 소비 칸(육성 소비·플레이 소비)에 놓고, 분류가 책의 정의인지 프로젝트 가정인지 표시해줘.
책 근거의 5단계 역할과, 내가 제공한 데이터에서 확인 가능한 사실을 구분해줘.
중복 집계 가능성, 유저군 불일치, 일회성 보상 혼입을 각각 표시해줘.
검증 전에 확정해야 할 데이터 소유자와 원천 표를 제안해줘.
3·4·5장에서 재계산할 값과 성공 기준을 변경 전후 비교 형식으로 적어줘.
```

</details>

> **확인 포인트**
>
> 결과가 일반 유저 기준 반복 생산을 `20×7+70=210개`, 계획 소비를 `150+80=230개`로 분리하고, 이벤트 100개를 같은 주간 반복 공급에 섞지 않았는지 확인합니다.
>
> 1장의 I/O 구조는 생산을 플레이 생산·활동 생산으로, 소비를 육성 소비·플레이 소비로 나눕니다(그림 1.3, 인쇄 5 / PDF 33). 스킬 자료에는 두 생산 칸의 경계 정의가 없으므로, 던전·주간 퀘스트·이벤트 보상을 어느 칸에 두었는지는 프로젝트의 분류(가정)로 표시돼야 합니다.

<a id="ch01-c"></a>

#### C. 보상 변경 2안의 전 과정 비교

서로 다른 보상안을 단순 지급량이 아니라 성장 주기·전투 리듬·검증 부담까지 포함해 비교합니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
일일 던전 보상 변경안 A와 B를 1장의 전체 프로세스로 비교해줘.
공통 가정: 강화석 장비 1개 총비용 900개, 목표 완성 기간 30일, 일반 유저 하루 1회 입장이다.
A안은 고정 30개 지급, B안은 고정 20개와 50% 확률로 추가 20개 지급이다.
둘 다 귀속 자원이며 거래·판매·추가 입장은 현재 없다. B안의 일별 추가 보상 판정은 독립이다.
우선 4장에서 일일 기대 생산과 30일 기대 생산을 계산해줘.
그 뒤 1장의 5단계별 입력·산출물·위험·검증 담당을 A/B 표로 비교해줘.
고정 보상과 확률 보상을 같은 "30개"라고 가정하지 말고 분산을 별도 표시해줘.
책 근거와 추가 제안, 확정 입력과 미확정 가정을 명확히 나눠줘.
3장의 전투 목표와 5장의 실제 도달률에 필요한 후속 데이터를 요청 목록으로 적어줘.
성공 기준은 30일 목표 달성 가능성, 공급 변동, 재검증 범위가 명확한 것이다.
```

</details>

> **확인 포인트**
>
> 계산 검수에서는 A안이 `900개/30일`에 정확히 맞고, B안의 기댓값도 `20+0.5×20=30개/일`이지만 획득 분산은 같지 않다는 점을 결과에 남겨야 합니다.

<a id="ch01-d"></a>

#### D. 5단계를 따라가는 단계별 학습 세션

실무 데이터를 아직 공개할 수 없을 때, 작은 합성 사례로 각 장의 입출력 관계를 익힙니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
1장의 5단계를 따라가는 45분 학습 과제를 설계해줘.
합성 사례: 적 HP 600, 고정 1회 피해 50, 초당 2회 공격, 첫 타격 0초다.
강화석은 일일 30개 생산, 장비 1단계 비용은 150개, 목표는 5일이다.
학습자는 전투·경제·수익화 경험이 없는 주니어 기획자다.
준비, 전투, 경제, 검증, 수익화 순서로 각 1개 과제와 산출물을 제시해줘.
계산 가능한 값은 직접 계산하되, 실제 프로젝트 값처럼 단정하지 말아줘.
각 단계에서 다음 단계로 넘길 데이터 필드를 표로 작성해줘.
책의 5단계 구조와 이 학습을 위한 추가 제안을 구분해줘.
마지막에는 오류를 찾는 검수 질문 6개와 채점 기준을 넣어줘.
성공 기준은 단위, 기간, 유저 가정, 변경 영향이 연결되는 것이다.
```

</details>

> **확인 포인트**
>
> 이 합성 사례의 고정 피해 가정에서는 `ceil(600/50)=12회`, 첫 타격 0초의 정확한 처치 시각은 `(12-1)/2=5.5초`, 장비 비용은 `150/5=30개/일`로 검산합니다.

<a id="ch01-followup"></a>

#### 후속. C에서 고른 보상안으로 5단계 변경 계약 갱신

[C. 보상 변경 2안의 전 과정 비교](#ch01-c)에서 고른 안과 미확정 값을 그대로 인용해 5단계의 변경 계약을 갱신합니다. 새 대화에서 쓸 때는 C의 결과표와 고른 이유를 인계 항목에 직접 붙여 넣습니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
1장 C에서 고른 일일 던전 보상안으로 다음 버전의 5단계 변경 계약을 작성해줘.
선행 결과·선택안: [A안 또는 B안, 고른 이유, C의 일일·30일 기대 생산과 분산 비교, 5단계 표]
유지할 확정 조건: 강화석 장비 1개 총비용 900개, 목표 완성 30일, 일반 유저 하루 1회 입장, 귀속 자원, 거래·판매·추가 입장 없음, B안 추가 보상의 일별 판정은 독립
미정 사항: [C에서 확정하지 못한 입력. 예: 3장 전투 목표, 5장 실제 도달률, 수익화 영향 범위]
이어받을 조건·예외: 아래 항목마다 판정(성립·불성립·미확인·해당 없음), 근거(원문 위치·입력·관측), 미확인 항목을 붙여줘.
- 고른 안의 기대 생산이 900개/30일과 맞고, 고정 보상과 확률 보상의 분산 차이를 남겼는가
- 던전 보상과 장비 강화 비용을 1장 I/O 구조의 어느 생산·소비 칸에 두었는가(칸의 경계 정의가 자료에 없으면 프로젝트 분류로 표시)
- 수익화를 설계 확정이 아닌 영향 확인 항목으로 둔 범위가 이번 버전에도 유지되는가
실제 데이터가 없는 항목은 계산 가정으로 표시하고, 기존 결론의 확정 사실로 승격하지 말아줘.
준비 단계의 목표 경험과 유저군이 여전히 유효한지 먼저 점검해줘.
전투·경제에서 바뀐 입력, 5장에서 재현할 검증 케이스, 수익화 영향 확인을 표로 연결해줘.
각 행에 단위·기간·원천·담당·승인 기준·되돌림 조건을 넣어줘.
계산 결과와 설계 판단, 책 근거와 추가 제안을 별도 열로 분리해줘.
다음 실험에서 한 번에 하나만 바꿀 매개변수와 비교 기준을 제안해줘.
완료 조건은 변경 전후를 같은 유저군·같은 기간으로 재현할 수 있는 것이다.
각 판정이 유지되거나 바뀐 이유, 새로 찾은 반례, 다음에 확인할 자료를 마지막에 남겨줘.
```

</details>

> **확인 포인트**
>
> 결과가 C의 900개·30일·하루 1회 조건을 그대로 쓰는지 확인합니다. B안을 골랐다면 기댓값이 `30개/일`로 같아도 분산이 다르다는 판정이 유지돼야 합니다. 인계한 판정이 바뀌었다면 바뀐 이유와 근거의 종류가 함께 남아야 합니다.

### 산출물과 검수 기준

- 산출물은 5단계 맵, 변경 영향 목록, 검증 순서입니다.
- 전투 보상과 경제 생산을 같은 것으로 중복 집계하지 않았는지 확인합니다.
- 모든 지표가 같은 기간·유저군인지 확인합니다.
- ‘좋아진다’ 대신 목표 전투 시간, 목표 도달 주기, 잔여 재화처럼 관찰 가능한 판정을 둡니다.

### 다른 장과 잇기

2장에서 목표 경험을 고정한 뒤 3·4장의 모델을 만듭니다. 5장의 결과가 허용 범위를 벗어나면 1장의 맵으로 돌아가 어느 단계의 입력을 조정할지 결정합니다. 8장은 이 맵을 재사용 가능한 모듈 계약으로 발전시킵니다.

## 2장 — 수치 구축 준비 작업: 숫자에 경험의 경계 조건 주기

### 사용할 상황

- 장르가 섞여 전투·성장·경제의 우선순위를 합의해야 할 때
- 타깃 게임을 참고하되 수치 복제를 피하고 싶을 때
- 콘텐츠, 수집, 난이도, 사회 기능 중 무엇이 대상 유저에게 중요한지 정리할 때

### 준비할 입력

- 장르 구성, 테마, 핵심 세션과 장기 목표, 대상 유저
- 성장·플레이·전투의 현재 기능 목록과 해금 조건
- 비교하려는 타깃 게임의 관찰 사실(추측과 실제 관찰은 나눠 기록)

### 사용 전략

1. 장르 이름을 하나로 고정하지 말고 각 요소가 책임질 경험과 측정할 결과로 분해합니다.
2. 테마가 약속하는 수집·전투·관계·자원 행동을 적고, 각 행동이 어떤 시스템에 연결되는지 확인합니다.
3. 유저 관점의 넓이·깊이·난이도와 기획 관점의 성장·플레이·전투를 한 표에 놓습니다.
4. 타깃 게임은 `유저/기획 목표 → 성장·플레이·경제 시스템 → 수익화` 순으로 역방향으로 읽습니다.
5. 비교 결과는 ‘가져올 숫자’가 아니라 ‘우리 프로젝트에서 검증할 가설’로 바꿉니다.

### 기본 요청 프롬프트

```text
[장르 요소]와 [테마]를 가진 게임을 준비 중이다.

2장의 넓이·깊이·난이도, 성장·플레이·전투 관점으로 설계 가설을 표로 만들어줘.
타깃 게임 [이름 또는 관찰 메모]는 목표→성장·플레이·경제 3시스템→수익화 순서로 역추론하되,

```

#### A. 장르와 테마를 수치 설계 조건으로 번역하기

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
협동 탐험 RPG와 마을 경영 요소를 결합한 게임의 준비 작업을 설계해줘.
테마는 "침수된 도시를 복구하는 탐험대"이고, 1회 세션은 12분이다.
목표 경험은 탐험의 긴장, 복구의 누적 성취, 동료 수집의 선택성이다.
초기 가정: 전투 1회 90초, 복구 1단계는 탐험 자원 120개를 소비한다.
2장의 장르·테마→유저 기대→수치 구조 순서로 가설을 표로 만들어줘.

넓이·깊이·난이도와 성장·플레이·전투를 같은 표에서 연결해줘.
책 근거, 내가 준 설계 조건, 추가 제안을 세 열로 분리해줘.
3장에 넘길 전투 리듬 변수와 4장에 넘길 생산·소비 변수를 명시해줘.
현재 값만으로 판단할 수 없는 점은 질문 또는 가정으로 표시해줘.
성공 기준은 장르명이 아니라 측정 가능한 경험·단위·주기로 번역되는 것이다.
```

>

#### B. 타깃 관찰 메모를 역추론 질문으로 바꾸기

외부 게임의 숫자를 복제하지 않고, 직접 관찰한 화면·플레이 기록에서 우리 프로젝트가 검증할 질문만 뽑아냅니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
타깃 게임을 참고하기 위한 관찰 메모를 2장의 역추론 틀로 정리해줘.
관찰 사실: 첫 20분에 장비 강화 2회, 보스전 1회, 동료 해금 1회가 있었다.
관찰 사실: 전투 패배 뒤 재도전 비용은 보이지 않았고, 상점 가격은 기록하지 못했다.
추론 금지: 타깃의 드롭률, 매출, 유저 비율, 내부 전투 공식은 알 수 없다.
유저/기획 목표 → 성장·플레이·경제 시스템 → 수익화 순서의 질문 표를 만들어줘.
목표는 유저 관점과 기획자 관점으로 나누고, 시스템 자리에 전투 구조를 넣지 말고, 수익화는 일반·유도·뽑기 결제로 나눠줘.
각 행을 관찰 사실, 합리적 가설, 확인 불가, 우리 프로젝트 검증 항목으로 구분해줘.
우리 게임의 10분 세션·30일 성장 목표에 옮길 수 있는 것은 가설로만 표현해줘.
책 근거와 추가 제안, 외부 사실 주장을 명확히 분리해줘.
3·4장에서 계측할 최소 데이터와, 관찰만으로 결론 내리면 안 되는 항목을 적어줘.
성공 기준은 타깃 숫자를 복사하지 않고 비교 가능한 설계 질문을 얻는 것이다.
```

</details>

>

>
> 질문 표의 순서는 목표(유저 관점과 기획자 관점) → 성장·플레이·경제 시스템 → 수익화(일반·유도·뽑기 결제)입니다(인쇄 23–24 / PDF 51–52). 전투 구조가 시스템 자리에 들어가지 않았는지, 기록하지 못한 상점 가격과 결제 설계가 수익화 행에서 확인 불가로 남았는지 봅니다.

<a id="ch02-c"></a>

#### C. 플레이어 유형과 난이도 범위를 설계하기

한 사람에게 하나의 유형을 붙이지 않고, 콘텐츠가 다양한 동기를 얼마나 다루는지와 입문·플레이·성장 난이도를 함께 봅니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
소규모 PvE 액션 게임의 유저 범위와 난이도 가설을 설계해줘.
가정 유저군: 빠른 전투를 좋아하는 사람, 수집 완성을 좋아하는 사람, 협동을 좋아하는 사람이 있다.
가정 콘텐츠: 8분 일반 임무, 15분 보스 임무, 주 1회 수집 도감 보상이다.
입문 목표는 첫 세션에 조작·성장·보상 루프를 모두 경험하는 것이다.
2장의 플레이어 유형을 고정된 인구통계가 아닌 콘텐츠 점검표로 사용해줘.
넓이·깊이·난이도와 성장·플레이·전투를 유저군별 표로 작성해줘.
입문·플레이·성장 난이도를 적 HP만으로 판단하지 않는 측정 항목을 제시해줘.
성장 난이도는 책의 정의대로 입문·플레이 난이도를 낮추는 과정에 상응하는 보상이 있는지로 측정해줘.
유저군을 바틀 유형에 대응시킨다면 유형 이름이 아니라 본문 정의에 따라 판단해줘.
책 근거, 제공한 가정, 추가 제안을 구분해줘.
3장과 4장에 전달할 최소 수치 입력과 아직 검증할 플레이 테스트 질문을 적어줘.
성공 기준은 한 유저군의 만족이 다른 유저군의 진입을 막는지 확인 가능한 것이다.
```

</details>

> **확인 포인트**
>
> 결과는 8분·15분·주 1회가 합성 입력임을 표시하고, 각 유저군의 실제 비율이나 선호 강도를 사실처럼 추정하지 않아야 합니다.
>
> 성장 난이도는 유저가 입문·플레이 난이도를 낮추는 과정에 상응하는 보상이 있는지로 정해집니다(인쇄 19 / PDF 47). 성장 난이도의 측정 항목이 성장 속도나 적 HP가 아니라 이 보상 대응을 보는지 확인합니다.
>
> 본문 정의에 따르면 킬러는 게임 세계의 운영이나 다른 플레이어의 게임 경험을 방해하는 것을 즐기는 유형입니다(인쇄 15 / PDF 43). PvE의 빠른 전투 선호를 곧바로 킬러에 대응시키지 않는지 확인합니다.

<a id="ch02-d"></a>

#### D. 수집·보상 시스템의 경험 가설 만들기

테마가 약속하는 수집 행동을 전투 보상·경제 소비·장기 목표에 연결하기 전에, 필요한 선택과 검증 지표를 설계합니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
도시 복구 테마의 수집·보상 시스템을 준비 단계에서 기획해줘.
합성 입력: 탐험 1회에 복구 재료 18개, 희귀 지도 조각은 25% 확률로 1개다.
복구 시설 1단계 비용은 재료 90개와 지도 조각 2개이며, 목표는 평균 5회 탐험이다.
재료는 귀속, 지도 조각은 거래 불가이며 시작 재고는 0, 각 탐험의 조각 판정은 독립이다.
계산 기준선에는 천장·추가 보상이 없고, 도입 여부는 미정 정책으로 분리해줘.
2장의 테마→유저 기대→성장·플레이·전투 관계로 설계 가설을 작성해줘.
관찰 가능한 입력과 아직 정하지 않은 정책을 분리하고, 책 근거와 추가 제안을 구분해줘.
5회까지의 기대 조각 수와 완성 확률, 조각 2개까지의 평균 시도 수를 따로 계산해줘.
재료도 모아야 하는 실제 완성 시도 수는 max(5, 조각 2개를 얻은 시도 수)로 구분해줘.
3장에 필요한 전투 보상 규칙, 4장에 필요한 I/O·가치 데이터, 5장 검증 항목을 목록화해줘.
확률 수량과 보장 규칙을 확정하기 전에는 어떤 결론을 유보해야 하는지 적어줘.
성공 기준은 테마의 수집 약속이 수치·주기·검증 항목으로 연결되는 것이다.
```

</details>

> **확인 포인트**
>
> 5회 기대 조각은 `1.25개`, 5회 이내 완성 확률은 약 `36.72%`입니다. 조각 2개까지 평균 `8회`이며, 재료 조건까지 포함한 평균 완성은 약 `8.4805회`입니다. 기대 수량·달성 확률·평균 완료 시점을 구분하고, 이 추가 확률 검산을 책이 제시한 원문 수치로 인용하지 않습니다.

### 다른 장과 잇기

2장의 우선순위는 3장의 속성·전투 플로, 4장의 경제구조, 7장의 단계 목표를 정하는 입력입니다. 1장의 프로세스 맵에 이 가설을 첫 단계 산출물로 남기고, 5장의 실제 결과로 가설을 수정합니다.

## 3장 — 게임의 전투 수치: 공식, 확률, 리듬을 분리해 설계하기

### 사용할 상황

- 공격·방어·체력, 치명·관통·회피, 스킬과 버프의 계산 순서를 정의할 때
- 직업, 몬스터, 보스의 생존 주기와 난이도를 역산할 때
- 표시 확률과 실제 발동 확률, 전투력과 실제 체감이 어긋날 때

### 준비할 입력

- 속성 정의, 공식, 적용 순서, 상한·하한·반올림, 스킬·버프 지속 조건
- 목표 전투 시간 또는 목표 턴 수, 1회 피해 또는 DPS, 공격 간격과 첫 타격 시점
- 레벨·직업·과금 수준·몬스터 유형별 입력값과 비교 구간

### 사용 전략

1. 속성 정의 → 전투 구조 → 능력치 정량화 → AI/NPC 순서로 문서를 만들게 합니다.
2. 기초 플로, 스킬 플로, 대미지 플로에서 입력·출력·판정 순서·재진입 조건을 분리합니다.
3. 공식은 저·중·고성장, 동레벨·레벨 차이, 서로 다른 유저 템플릿에 대입해 구간별 결과를 비교합니다.
4. 확률은 표시값이 아니라 경로 확률로 계산합니다. 순차 판정에서 앞 조건을 통과해야 하는 결과는 앞 조건의 확률을 곱합니다.
5. 전투력 합계와 DPS·생존·회복·제어 리듬을 별도 표로 보고, 마지막에는 전투 시뮬레이션으로 확인합니다.

### 가정 예시: 단위와 순서 확인

가정 예시로 공격력 `A=100`, 방어력 `D=100`을 책의 나눗셈 예시 `피해=A²/(A+D)`에 넣으면 1회 피해는 `50`입니다. 적 체력이 `1,000`이면 고정 피해 가정에서 필요 타격 수는 `ceil(1,000/50)=20회`입니다. 초당 2회 공격하고 첫 타격이 0초라면 처치 시각은 `(20-1)/2=9.5초`입니다. 이는 1회 피해·고정 간격·첫 타격 조건을 둔 가정 예시이며, 회피·치명·회복·행동 지연이 있는 실제 전투에 그대로 대입하지 않습니다.

#### A. 비선형 수식과 버프 적용 위치 비교

```text

합성 입력: 레벨 1에서 30까지 총 공격력 증가 예산은 150이고, 기준 공격력은 100이다.

3장의 성장 구축→성장 분할→성장 세분화 순서로 표를 만들어줘.
각 루트의 총량·개방 조건·횟수·회당 증가·실제 도달률 가정을 분리해줘.
60/25/15%는 기준 공격력 100이나 다른 속성 예산이 아니라, 같은 부모인 총 증가 예산 150에만 적용해줘.
회차별 증가량과 현재 단계까지의 누적 증가량을 서로 다른 열로 두고, 둘을 중복 합산하지 마.
이 분할을 합 100%가 필수인 글로벌 분할로 검사하고, 벤치마크 분할이라면 합 100%가 필요 없다는 차이를 따로 적어줘.
방어·체력도 같은 루트로 나눈다면 1단계 공격·방어·체력의 총 분할 비율을 서로 같게 둘지 확인해줘.
책 근거, 제공한 총예산, 추가 제안을 구분하고 누락된 비용·보상 연결은 4장 입력으로 표시해줘.
레벨 1·10·15·30에서 가능한 최소·기대·완성 템플릿을 어떻게 검증할지 제안해줘.
기대 템플릿에 책의 목표 비율 60%를 쓴다면 원문 예시값으로 표시하고 레벨업 60%와 구분해줘.
1단계 비율을 고정해도 레벨별 전투 사이클은 바뀔 수 있다. 사이클을 다시 계산하려면 성장식과 피해식이 함께 필요하므로, 그 입력이 있는지 판정(성립·불성립·미확인·해당 없음)하고 빠진 입력을 적어줘.
총량 150을 여러 루트에 중복 배정하지 않는 합계 검수를 포함해줘.
성공 기준은 유저 템플릿별 공격력과 성장 수익을 재현하고 비용과 연결할 수 있는 것이다.
```

</details>

> **확인 포인트**
>
> 주어진 분할만 계산하면 레벨업 `90`, 장비 `37.5`, 스킬 `22.5`로 합계 `150`이지만, 실제 구현에서는 정수 반올림·단계 수·개방률을 별도 규칙으로 확정해야 합니다.
>
> 60/25/15%는 같은 부모(총 증가 예산 150)를 나누는 글로벌 분할이므로 합 100%가 필수입니다(인쇄 73–74 / PDF 101–102). 벤치마크 분할은 합이 100%가 아니어도 되며(인쇄 73 / PDF 101), 하위 밸런스를 유지하려면 1단계 공격·방어·체력의 총 분할 비율을 서로 같게 둡니다(인쇄 75 / PDF 103). 결과가 여러 속성 열을 통틀어 100%인지 검사하지 않는지도 봅니다.
>
> 원문 표 3.5는 `1:1:10` 선형 성장을 업그레이드 뺄셈(`K=2000`)에 넣어 사이클이 1레벨 10.03턴에서 100레벨 13턴으로 늘어납니다(인쇄 70 / PDF 98). 표 3.6은 치명 공격·방어 관통을 더해 사이클이 9.95턴에서 6.93턴으로 줄어듭니다(인쇄 71 / PDF 99). 이 입력에는 공격력 예산만 있고 방어·체력 성장과 피해식이 없으므로, 사이클 재계산을 미확인으로 두고 필요한 입력을 요청하는지 확인합니다.
>
> 유저 템플릿의 목표 비율 60%는 초안의 레벨업 60%와 다른 값입니다. 원문은 실제 속성 비율의 60%를 합격점으로 삼아 템플릿을 만들고(인쇄 89 / PDF 117), 이 표를 실제 성장 데이터로 교체할 임시 템플릿으로 봅니다(인쇄 90 / PDF 118). 결과가 60%를 기대 템플릿의 규칙으로 쓰지 않는지 확인합니다.

전투력 합계만 맞추지 않고, 탱커·딜러·힐러의 생존·피해·회복 주기와 NPC 보정을 따로 봅니다.

<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
협력 PvE의 탱커·딜러·힐러와 보스 NPC 리듬을 검토해줘.

보스의 목표 생존 주기는 20초이고, 플레이어의 목표 생존 주기는 10초라는 설계 가정이다.
탱커는 생존, 딜러는 DPS, 힐러는 단위시간 회복과 파티 생존 기여로 평가한다.

회복, 제어, 다수전, 이동 지연이 없는 가정의 한계를 명시해줘.
이 보스 보정을 난이도가 비슷한 다른 NPC에 재사용한다면, 적용 시나리오와 디폴트 매개변수를 바꿀 때 재참조되는 데이터가 함께 바뀌는지 확인 항목으로 적어줘.
성공 기준은 역할별 지표와 NPC 난이도 보정이 같은 시간 단위를 쓰는 것이다.
```

> **확인 포인트**
>
> 고정 피해·공격 간격 가정에서 보스는 `ceil(3,000/150)=20회`가 필요해 처치 시각이 19초이므로, 목표 20초와의 1초 차이는 버프·패턴을 넣기 전의 기준선으로만 해석합니다.
>
> 책의 NPC 예시는 표준 생존 주기 10턴에서 보스 20턴·플레이어 10턴이고(인쇄 91 / PDF 119), 흔한 생존 주기 범위도 6~20턴으로 적습니다(인쇄 58 / PDF 86). 이 예시의 20초·10초와 같은 척도로 비교하거나 책의 범위 안이라고 판정하지 않는지 확인합니다. 협력 삼대장은 가치 밸런스와 역할 밸런스를 모두 맞춰야 하므로(인쇄 62 / PDF 90), 탱커의 생존 주기와 힐러의 단위시간 치유도 같은 시간 단위로 남아야 합니다.
>
> 책의 AI(3.4절)는 NPC 속성을 정량화하는 기본 응용과 고착 지점·세계 번영과 유저 매칭 같은 고급 응용으로 나뉩니다(인쇄 88–89 / PDF 116–117). 스킬 정리: NPC 행동 패턴 설계는 이 범위에 들지 않습니다. 행동 AI 규칙이 책 근거가 아니라 추가 제안으로 남는지 확인합니다.
>
> 원문은 난이도가 비슷한 플레이에서는 속성 템플릿을 다시 설정하지 않고 재사용할 수 있다고 하지만, 적용 시나리오를 명확히 해야 한다고 합니다. 이후 디폴트 매개변수를 최적화하면 재참조되는 데이터도 함께 바뀌므로 적용 가능한지 확인해야 한다고도 합니다(인쇄 93 / PDF 121). 이 보정을 다른 NPC에 옮길 때 이 확인을 남기는지 봅니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible

선행 결과·선택안: [순차 또는 원탁 중 고른 모델과 이유, B의 결과별 확률표]
유지할 확정 조건: 명중 h=0.70, 관통 p=0.30, 치명 c=0.05, 우선순위 명중→관통→치명, 관통·치명은 동시 결과가 아님, 원탁의 초과분은 뒤 칸에서 잘라냄

- 조건부 확률로 쓴 순차 모델의 p·c와 칸 비중으로 쓴 원탁의 값을 같은 표시값으로 섞지 않았는가
- 고른 모델에 맞춰 2단계 속성의 성장 범위를 정했는가(원탁이면 2단계 수치 조정을 제한하고, 순차 모델이면 범위가 더 커질 수 있으며, 원문의 100레벨 50%는 확률론 알고리즘을 가정한 예시)

각 테스트에 입력·단위·난수 시드 또는 기댓값 기준·예상 결과·허용 오차를 적어줘.
저·중·고 성장, 동레벨·레벨 차이, 역할별 리듬, 분모 0·피해 0 경계를 포함해줘.
순차와 원탁 중 선택한 모델의 확률 합·탈락 결과·동시 발생 정책도 검증해줘.
책 근거의 구조와 추가로 제안하는 자동화·시뮬레이션 절차를 분리해줘.
4장의 성장 비용과 5장의 실제 도달 속성으로 갱신해야 할 입력을 목록화해줘.
완료 조건은 전투 변경 전후를 같은 가정에서 비교하고 실패 원인을 플로 단계로 추적하는 것이다.
각 판정이 유지되거나 바뀐 이유, 새로 찾은 반례, 다음에 확인할 자료를 마지막에 남겨줘.
```

> **확인 포인트**
>
> 순차 모델을 골랐다면 관통 `21%`·치명 `2.45%`·일반 `46.55%`·빗나감 `30%`, 원탁을 골랐다면 `30%`·`5%`·`35%`·`30%`가 테스트의 기댓값으로 그대로 이어지는지 확인합니다. 고르지 않은 모델의 값이 기댓값에 섞이면 인계가 실패한 것입니다.
>
> 원문은 확률론 알고리즘이면 2단계 속성값의 범위가 더 커질 수 있고 우선순위가 낮은 속성일수록 더 클 수 있다고 합니다. 원탁 이론 알고리즘이면 2단계 속성의 수치 조정을 제한해야 한다고도 합니다(인쇄 71 / PDF 99). 100레벨 50%는 확률론을 가정한 원문 예시이므로(인쇄 71 / PDF 99), 원탁을 골랐을 때 이 값을 성장 테스트의 상한으로 그대로 옮기지 않는지 봅니다.

### 산출물과 검수 기준

- 산출물은 속성 사전, 전투 플로, 구간별 피해·생존 표, NPC 보정안, 테스트 케이스입니다.
- 퍼센트 보너스가 중간식인지 최종식인지, 가산인지 곱연산인지 분명한지 봅니다.
- `HP/피해`의 단위를 턴·타격·초 가운데 하나로 고정했는지 확인합니다.
- 실제 피해가 0이거나 음수일 때의 하한 정책을 정의했는지 확인합니다.
- 공격 종류가 늘면 대응하는 방어 종류와 밸런스 복잡도, 유저의 입문 난이도와 성장 난이도가 함께 오르므로(인쇄 28 / PDF 56), 새 속성에 목적과 대응 공식이 있는지 봅니다.
- 성장 분배는 동일 부모·속성별 예산에서 계층 비율을 곱하고, 강화 표의 누적 지급과 회차 지급을 구별합니다. 합 100% 검사는 글로벌 분할에만 적용합니다. [성장 분배 산식](../.agents/skills/game-balance-bible/references/combat-formulas.md#성장-구축분할세분화)을 함께 읽습니다.
- 세분화 전에 각 루트가 성장형·수집형·하이브리드형(인쇄 79 / PDF 107) 또는 랜덤형(인쇄 87 / PDF 115) 중 무엇인지 정합니다. 랜덤형은 유저가 더 추구하거나 실제 수익이 더 높은 속성을 기준으로 세분화합니다(인쇄 87–88 / PDF 115–116).
- 전투력 계수는 1단계 속성이면 하위 밸런스의 속성 가중치(예: `1:1:10`이면 `1, 1, 0.1`)로, 2·3단계 속성이면 실제 피해 수익으로 구합니다(인쇄 98 / PDF 126).
- 순차 판정과 원탁 방식, 확률 합계, 낮은 우선순위 결과의 탈락 여부를 확인합니다.

### 다른 장과 잇기

3장의 성장 분배는 4장의 비용·보상으로 현실화되고, 5장은 그 결과로 실제 유저 속성 및 PvE·PvP를 검증합니다. 7장은 전투 시간·단일 피해의 변화가 리듬에 만드는 공백을 보고, 8장은 전투 기본 모델과 몬스터 난이도 모델의 연결을 명시합니다. 자세한 공식은 [전투 공식 참고](../.agents/skills/game-balance-bible/references/combat-formulas.md)를 확인합니다.

## 4장 — 게임의 경제 수치: 재화 총량과 가치의 계약 만들기

### 사용할 상황

- 강화 비용, 일일 보상, 이벤트, 드롭 테이블을 하나의 경제 흐름으로 바꿀 때
- 재화 부족·누적, 성장 모듈 간 비용 경쟁, 가성비 차이를 분석할 때
- 랜덤 보상이나 거래 가능 재화의 공급을 변경할 때

### 준비할 입력

- 화폐·자원 목록, 귀속/유통 여부, 생산 루트, 소비 루트, 환전·거래 규칙
- 성장 단계별 비용, 목표 주기, 일회성·반복 생산, 유저군별 참여율
- 드롭의 가중치·확률·수량 분포·보장 조건과 가치 단위

### 사용 전략

1. 경제모델의 통제 수준과 거래 조건을 먼저 고르고, 화폐와 자원의 역할을 분리합니다.
2. I/O 표에 모든 생산·소비·판매·선물·이벤트·환전을 넣되 일회성과 반복 생산을 구분합니다.
3. 성장 소비 총량과 목표 주기로 일일 생산을 역산한 뒤 플레이별 공급으로 나눕니다.
4. 랜덤 보상은 가중치에서 실제 확률을 구하고, 수량·천장·다중 보상 조건을 분리해 기대 생산을 계산합니다.
5. 가성비 비교 전에 돈·시간·전투력 등을 하나의 가치 기준으로 환산하고, 증가계수와 유저군별 참여율을 적용해 봅니다.

### 가정 예시: 기간과 총량 확인

가정 예시로 한 재화의 30일 총생산이 `3,000`, 같은 30일 총소비가 `3,600`이면 잔여량은 `-600`, 잔여 비율은 `(-600)/3,600=-16.67%`입니다. 이 비율의 분모는 소비이며, 소비가 0이면 정의되지 않습니다. 30일 생산에서 1일 소비를 빼거나 초기 보유량을 잔여량에 섞지 않습니다. 목표값은 게임·재화·세그먼트의 정책이므로 이 숫자를 보편 임곗값으로 쓰지 않습니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
```

> **확인 포인트**
>
> 주간 반복 기준 강화석은 `40×7=280개`, 계획 소비는 250개라서 잔여 `30개`를 계산하되, 신규 유저 1회 100개는 일반 유저의 반복 주간 공급과 분리해야 합니다.
>
> 저자는 계획·시장경제 게임에는 삼원화 화폐 구조가 좋다고 합니다(인쇄 120 / PDF 150). 이 입력에는 거래 코인 하나만 화폐로 정의돼 있으므로, 결과가 화폐 구조를 적합하다고 단정하지 않고 미확인으로 둔 뒤 빠진 화폐 정의를 요청하는지 확인합니다.
>
> 책의 사례는 상회처럼 시스템이 중간 저장소인 거래에서 귀속 화폐만 주고 그 자원의 2차 거래를 막습니다(인쇄 115 / PDF 145). 또 가격 민감형·협의형 자원을 익명·실명 거래로 나누고 부캐 전달에 거래 한도를 둡니다(인쇄 114 / PDF 144). 강화석은 거래·환전·선물이 불가하므로 부캐 전달 한도는 강화석에 해당 없음이고, 코인 거래소의 방식·거래 품목·한도·가격 변동은 입력에 없어 나머지 장치가 미확인으로 남는지 확인합니다. 저장 거래 시스템의 재고·가격·세금 설계는 저자가 ‘개인적 생각이니 참고만 바란다’고 밝힌 의견이므로(인쇄 117 / PDF 147), 책의 규칙으로 인용하지 않아야 합니다.
>
> 저자는 계획경제도 시장경제처럼 거시경제와 미시경제에 미치는 영향을 모두 고려해야 하되, 통제할 자원 종류가 적어 오류 위험이 크게 줄어든다고 합니다(인쇄 107 / PDF 137). 결과가 계획경제라는 이유로 거시·미시 영향 확인을 생략하지 않는지 봅니다.

#### B. 목표 주기에서 보상을 역산하는 생산 모델

목표 육성 기간과 자원별 총비용을 먼저 정한 뒤, 플레이 루트별 공급·참여율·일회성 보상을 분리해 역산합니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
장비 강화 목표 주기에서 일일 보상을 역산하는 생산 모델을 만들어줘.
합성 입력: 장비 1개 총비용은 강화석 1,200개와 코인 6,000개, 목표 주기는 30일이다.
일반 유저는 일일 던전 1회, 집중 유저는 추가 콘텐츠까지 참여하지만 실제 참여율은 미정이다.
강화석은 던전·주간 퀘스트에서, 코인은 던전·상점 판매에서 생산할 계획이다.
30일 반복 생산만으로 자원별 필요 일일 공급을 먼저 계산해줘.
그 뒤 생산 분배·생산 매개변수·증가계수·유저군별 투입 비율을 넣을 표를 제안해줘.
주간 퀘스트·이벤트·판매 지급을 일일 반복 생산에 자동 합산하지 말아줘.
책 근거, 제공한 비용·기간, 추가 제안과 미정 참여율을 구분해줘.
유저군별 실제 목표 주기가 달라질 때 다시 계산할 값과 검수 기준을 적어줘.
이 총비용은 가치 체계를 만들기 전 구축 단계의 소비값이라는 점을 밝히고, 가치 체계를 만든 뒤 소비 모델을 다시 조정할 때 확인할 항목을 적어줘.
가치 환산 전에 자원 개수와 가치 합계를 서로 더하지 않도록 경고해줘.
지금 정할 수 없는 매개변수는 건너뛰거나 임시로 정의했다고 표시하고, 모델 완성 뒤 검증에서 최적화할 항목으로 남겨줘.
성공 기준은 각 자원의 총비용·목표 기간·공급 루트가 같은 단위로 역산되는 것이다.
```

</details>

> **확인 포인트**
>
> 가정한 목표의 최소 반복 공급은 강화석 `1,200÷30=40개/일`, 코인 `6,000÷30=200개/일`이며, 참여율·일회성 지급·증가계수는 이 기준을 대체하지 않고 별도 조정 입력입니다.
>
> 저자는 구축 단계의 소비 모델이 완전하지 않아 그 소비 수치는 생산 모델 설계용 데이터일 뿐이며, 가치 체계를 구축한 뒤 소비 모델을 다시 조정한다고 합니다(인쇄 136–137 / PDF 166–167). 결과가 총비용 `1,200개`·`6,000개`를 최종 소비값처럼 확정하지 않고 재조정 단계를 남기는지 확인합니다. 저자는 공식만으로 소비 모델을 완성할 수 없고 소비량·생산량·가격·수익 데이터를 함께 맞추는 것이 가장 중요하다고 씁니다(인쇄 136 / PDF 166). 재조정 항목에 이 네 데이터가 들어가는지도 봅니다.
>
> 저자는 현재 단계에서 계산하거나 설정할 수 없는 매개변수는 건너뛰고 나중에 설정해도 된다고 합니다(인쇄 150 / PDF 180). 정확하지 않으면 이해와 느낌으로 임시 정의하고, 모델을 완성한 뒤 검증에서 최적화한다고 씁니다(인쇄 151 / PDF 181). 미정 참여율을 근거 없이 확정하지 않고 임시값 표시와 최적화 단계를 남기는지 확인합니다.

#### C. 가중치 드롭 테이블과 기대 공급 검증

가중치 하나를 바꿀 때 다른 결과의 실제 확률과 경제 총량도 함께 갱신하도록, 수량 분포·천장·반복 횟수를 분리합니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
던전 보상 상자의 가중치 변경 전후 기대 공급을 검토해줘.
합성 풀: 강화석 4~8개가 가중치 50, 코인 100개가 가중치 30, 꽝이 가중치 20이다.
강화석 수량은 성공 시 4·5·6·7·8개가 같은 확률이라는 가정이다.
상자는 하루 1회 열고, 천장·보장·다중 보상·추가 드롭은 아직 없다.
변경안은 강화석 가중치 50을 40으로 낮추고 다른 가중치는 유지하는 것이다.
변경 전후 전체 가중치, 실제 획득 확률, 강화석·코인 기대 생산을 표로 계산해줘.
가중치와 고정 확률을 같은 것으로 취급하지 말고, 책 근거·제공 규칙·추가 제안을 분리해줘.
수량 기댓값과 시도당 기댓값, 성공 조건부 평균을 따로 표시해줘.
천장이나 다중 보상을 도입할 때 표준 풀에서 분리해 다시 계산할 필드를 적어줘.
4장 I/O와 5장 검증에 넘길 일·주·30일 기대 공급도 제안해줘.
성공 기준은 모든 결과 확률의 합과 변경 후 총 공급 변화가 재현되는 것이다.
```

</details>

> **확인 포인트**
>
> 검산하면 변경 전 총가중치 100에서 강화석 확률 50%, 시도당 기대 강화석은 `0.5×6=3개`이며, 변경 후 총가중치 90에서 강화석 확률은 `40/90≈44.44%`, 시도당 기대 강화석은 `≈2.667개`입니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
장비 강화와 던전 플레이의 가치·가성비 비교 초안을 검토해줘.
합성 입력: 강화석 200개 단가 2, 코인 10,000개 단가 0.01, 강화 전투력 가치는 150이다.
별도 비교안은 강화석 600개 단가 0.5, 전투력 가치 150이며 코인 비용은 포함하지 않는다.
두 사례는 전제가 다르므로 같은 표의 합계나 직접 우열로 해석하면 안 된다.
4장의 공통 가치 기준→성장 가성비→플레이 가성비 순서로 계산표를 작성해줘.
각 값의 단위·출처·포함 비용을 명시하고, 책 근거·제공 입력·추가 제안을 구분해줘.
첫 사례의 총 소비 가치와, 두 번째 사례의 성장 가성비를 각각 계산해줘.
첫 사례의 소비 가치와 전투력 가치가 다를 때 설계 오류로 볼지, 책의 피팅 관계로 볼지 판정해줘.
플레이 가성비는 책의 식대로 분모를 플레이에 소비한 시간 가치로 두고, 계산에 더 필요한 데이터를 적어줘.
재료·사회 비용을 분모에 넣는다면 책의 식이 아닌 프로젝트 확장으로 따로 표시해줘.
제공한 단가가 책의 가격 책정 순서(화폐와 전투력에 먼저 가격을 매기고, 그다음 소비 모델을 참고해 자원 가격을 정함)로 정해졌는지 판정하고, 입력에 근거가 없으면 미확인으로 둬줘.
가성비가 실제 재미·매출·평판을 증명하지 않는다는 한계를 검수 항목으로 넣어줘.
성공 기준은 분자·분모가 같은 가치 단위이고 서로 다른 전제를 섞지 않는 것이다.
```

</details>

> **확인 포인트**
>
> 첫 사례의 소비 가치는 `200×2+10,000×0.01=500`, 두 번째 사례의 성장 가성비는 `150÷(600×0.5)=0.5`입니다. 각 단가는 같은 가치 기준을 뜻하는 가정이며, 다른 수량·포함 비용의 전제를 섞지 않습니다.
>
> 플레이 가성비의 분모는 유저가 그 플레이에서 소비한 시간 가치입니다(인쇄 172 / PDF 202). 결과가 시간 외 비용을 책의 식처럼 분모에 넣지 않고, 넣을 경우 시간과 이중 계산되지 않게 같은 가치 단위로 환산하는 확장으로 표시하는지 확인합니다.
>
> 저자는 기준점이 되는 화폐·자원·속성의 가격을 감성으로 정할 수 있다고 하고(인쇄 163 / PDF 193), 가격은 화폐와 전투력에 먼저 매긴 뒤 소비 모델을 참고해 자원 가격을 정한다고 합니다(인쇄 164 / PDF 194). 이 입력의 강화석 단가는 그 순서로 정했다는 근거가 없으므로 미확인으로 남는지 확인합니다.
>
> 첫 사례의 소비 가치 `500`과 전투력 가치 `150`이 다르다는 것만으로 설계 오류로 판정하지 않는지 확인합니다. 표 4.37 노트는 전투력 가치가 대부분 소비 가치와 같지 않으며, 소비 모델은 전투력 가치를 참조해 소비 데이터를 피팅한다고 설명합니다(인쇄 170 / PDF 200). 저자는 가격을 책정할 때 비용이 가장 놓치기 쉽다고 보고, 비용에 사회적 비용과 게임 난이도까지 넣습니다(인쇄 168 / PDF 198). 두 번째 사례가 코인 비용을 뺀 전제를 결과에 남기는지도 봅니다.

<a id="ch04-e"></a>

#### E. 책 예시의 화폐 비율과 표별 코인 단가를 섞지 않고 재현하기

A~D는 가정 입력이라 책의 표와 맞춰 볼 수 없습니다. 이 보완 예시는 책의 가치 체계 예시를 재현할 때 화폐 비율과 표마다 다른 코인 단가를 구분하는 연습입니다. 아래 숫자는 [경제 모델 참고](../.agents/skills/game-balance-bible/references/economy-models.md#원문-예시의-화폐-비율-불일치)에 적힌 책의 예시값이며, 다른 프로젝트의 권장값이 아닙니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
4장 가치 체계의 책 예시를 표마다 따로 재현해줘. 원문 PDF는 열지 말고 스킬 자료에 적힌 값과 위치만 써줘.
확인할 값 1: 본문의 RMB:다이아:귀속 다이아=1:10:10이 표 4.33의 구매력, 표 4.34의 단가와 일치하는가
확인할 값 2: 인쇄 163쪽 예시와 인쇄 165쪽 표 4.34의 코인 단가 0.0001과 표 4.12·표 4.39의 코인 단가 0.001
확인할 값 3: 표 4.12·4.17의 전투력 가치(레벨 1은 90, 합계 17,820)와 표 4.36의 전투력 가치(9, 1,782)
재현할 계산 1: 장비 강화석 100,000개×1 + 코인 10,000,000개×0.0001의 소비 가치
재현할 계산 2: 표 4.39의 일일 퀘스트 수익 150,000×0.001 + 60×0.1 + 208×0.5
각 확인 항목에 판정(성립·불성립·미확인·해당 없음)과 근거 위치를 붙이고, 어긋나는 값은 어느 화폐의 어느 표인지 밝혀줘.
표 4.39를 0.0001로 다시 계산하면 얼마가 되는지 비교하되, 두 표의 단가를 한 계산에 섞지 마.
확인할 값 3의 두 전투력 가치는 10배 차이가 나는지 판정하고 두 표의 비율을 섞어 비교하지 마.
책의 서술, 스킬 정리, 내 계산 요청을 구분하고, 어떤 비율도 우리 프로젝트의 권장값으로 쓰지 마.
원문과 직접 대조할 쪽수 목록을 마지막에 남겨줘.
```

</details>

> **확인 포인트**
>
> `1:10:10`은 본문·표 4.33·표 4.34가 서로 일치하므로 성립입니다(인쇄 165 / PDF 195). 같은 장에서 어긋나는 것은 코인 단가로, 인쇄 163쪽 예시와 인쇄 165쪽 표 4.34는 `0.0001`, 표 4.39는 `0.001`입니다(인쇄 163·165·173 / PDF 193·195·203). 가치 체계 전의 표 4.12도 변환 관계를 ‘일단 과감하게 설정’한 임시값으로 코인 단가 `0.001`을 씁니다(인쇄 140 / PDF 170). 계산 1은 `100,000+1,000=101,000`, 계산 2는 `150+6+104=260`입니다. 표 4.39를 `0.0001`로 바꾸면 `15+6+104=125`가 되어 표의 `260`과 맞지 않습니다. 결과가 화폐 비율 자체를 본문과 표의 불일치로 설명한다면 스킬 자료와 다르므로 근거 위치를 다시 확인합니다.
>
> 전투력 가치도 표마다 기준이 다릅니다. 표 4.12·4.17의 레벨 1 `90`과 합계 `17,820`(인쇄 140·145 / PDF 170·175)은 본문 단가 기준이고, 표 4.36의 `9`와 `1,782`(인쇄 166–167 / PDF 196–197)는 이와 10배 차이가 납니다. 결과가 두 표의 비율을 섞어 비교하지 않는지 확인합니다.

#### 후속. C의 가중치 변경안을 I/O 검증 계획으로 발전시키기

[C. 가중치 드롭 테이블과 기대 공급 검증](#ch04-c)에서 고른 가중치안을 검증 가능한 경제 실험으로 바꾸고, 실측값이 없으면 가정을 유지합니다. 새 대화에서는 C의 확률·기대 생산 표와 이 상자가 들어갈 I/O 표를 인계 항목에 직접 적습니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
4장 C에서 고른 상자 가중치안과 [I/O 표], [가치 기준]을 같은 I/O 계약의 검증 계획으로 발전시켜줘.
선행 결과·선택안: [변경 전 가중치 50 또는 변경 후 40 중 고른 안과 이유, C의 실제 확률·기대 생산 표]
유지할 확정 조건: 강화석 4~8개 균등 수량·가중치 50(변경안 40), 코인 100개 가중치 30, 꽝 가중치 20, 하루 1회 개봉, 천장·보장·다중 보상·추가 드롭 없음
미정 사항: [참여율, 가격, 천장 도입 여부 등 C에서 정하지 않은 축]
이어받을 조건·예외: 아래 항목마다 판정(성립·불성립·미확인·해당 없음), 근거(원문 위치·입력·관측), 미확인 항목을 붙여줘.
- 가중치 하나를 바꾼 뒤 다른 결과의 실제 확률과 총 기대 공급을 다시 계산했는가
- 성공 조건부 평균과 시도당 기댓값을 분리했는가
- 드롭 유형을 확률 방식으로 바꾸면 판정 순서 때문에 뒤에 놓인 항목의 실제 확률이 표시값보다 낮아지는가(지금처럼 가중치 방식이면 해당 없음)
실제 로그가 없는 생산·참여율·가격은 계산 가정으로 표시하고, 합성 기댓값을 실측값처럼 쓰지 말아줘.
자원별로 기간·유저군·반복/일회성·귀속/유통·생산 원천·소비처를 재확인해줘.
변경 전후의 실제 확률, 기대 생산, 총소비, 잔여량, 가치 기준을 같은 기간으로 비교하는 표를 작성해줘.
천장·판매·환전·이벤트가 추가될 때 독립 행으로 넣을 규칙도 적어줘.
책 근거의 경제 순서와 추가로 제안하는 계측·경보 기준을 구분해줘.
5장에 넘길 유저군별 지갑·도달 단계·공유 재화 제약 데이터를 목록화해줘.
완료 조건은 공급 변경의 효과와 부작용을 같은 I/O 계약에서 추적할 수 있는 것이다.
각 판정이 유지되거나 바뀐 이유, 새로 찾은 반례, 다음에 확인할 자료를 마지막에 남겨줘.
```

</details>

> **확인 포인트**
>
> 변경 후를 골랐다면 총가중치 `90`, 강화석 확률 `40/90≈44.44%`, 시도당 기대 강화석 `≈2.667개`가 검증 계획의 기준선으로 그대로 이어지는지 확인합니다. 확률 방식 드롭 패키지로 바꾸는 안이 나오면 판정 순서를 반영한 확률로 기대 생산을 다시 계산해야 합니다(인쇄 159 / PDF 189).

### 산출물과 검수 기준

- 산출물은 자원 사전, I/O 표, 소비·생산 모델, 드롭 기댓값 표, 가치 기준 표입니다.
- 같은 재화를 여러 성장 모듈의 가용량으로 중복 썼는지 확인합니다.
- 소비는 성장 모듈·플레이 모듈·기타 모듈 소비로 나누며, 이 단계에서 세분화하는 것은 성장 모듈 소비입니다(인쇄 137 / PDF 167).
- 저자는 유저 거래를 생산 채널에 포함하지만(인쇄 117 / PDF 147), 생산 모델을 만들 때는 시스템 생산과 유저 간 거래로 얻는 양을 구분해 계산합니다(인쇄 152 / PDF 182).
- 실제 확률의 합, 가중치 변경 뒤 다른 항목의 확률·총기댓값 변화를 다시 계산합니다.
- 성장 가성비와 플레이 가성비의 분자·분모가 같은 가치 또는 시간 단위인지 확인합니다.
- ‘판매 가능한 성장 소비 규모’를 실제 매출·재미·평판과 동치로 해석하지 않습니다.

### 다른 장과 잇기

2장의 성장·플레이 구조가 I/O의 루트를 정하고, 3장의 속성 수익이 소비 모델의 가치 판단에 연결됩니다. 5장은 주기별 생산·소비·잔여와 도달 레벨을 검증하며, 6장은 수익화 변경이 이 흐름에 더하는 생산·소비를 따로 재검증합니다. 산식은 [경제 모델 참고](../.agents/skills/game-balance-bible/references/economy-models.md)를 확인합니다.

## 5장 — 게임 수치 검증: 유저 경로를 역방향으로 재생하기

### 사용할 상황

- 보상과 비용을 만들었지만 실제 유저가 어느 레벨·강화 단계에 도달하는지 불확실할 때
- 특정 레벨에서 난이도 급등, 재화 막힘, 유저군 간 격차가 보일 때
- 전투식은 맞지만 경제·성장과 합친 실제 전투 결과를 확인할 때

### 준비할 입력

- 기간별 계획 생산과 추가 생산, 초기 보유량, 소비 우선순위와 모듈별 누적 비용
- 경험치·레벨 표, 해금 상한, 성장 모듈별 속성·전투력 표
- 세그먼트 정의, 몬스터 난이도 표, 전투 공식과 비교할 목표 결과

### 사용 전략

1. 생산 검증에서 계획 생산과 이벤트·퀘스트·상점 같은 추가 생산을 동일 기간으로 누적합니다.
2. 소비 검증에서 해당 시점에 접근 가능한 성장 모듈과 플레이 소비를 모두 합산합니다.
3. `잔여량=총생산-총소비`, `잔여 비율=(총생산-총소비)/총소비`를 같은 기준으로 계산하고, 소비가 0인 행은 별도 처리합니다. 실제 잔고는 `초기 보유량+유입-실제 지출`로 별도 추적합니다. 계획 소비가 공급보다 큰 음수 잔여량을 실제로 이미 지출한 음수 지갑으로 해석하지 않습니다.
4. 누적 경험치와 누적 비용을 오름차순 기준값 테이블에 퍼지 매칭해 도달 레벨·모듈 수준을 구합니다. 공유 재화라면 `모듈별 소비 합≤가용량` 제약을 먼저 적용합니다.
5. 그 유저 템플릿을 3장의 전투 모델과 몬스터 표에 넣고, 경제 → 성장 → 전투 결과의 인과를 기록합니다.

### 가정 예시: 공유 재화의 제약

가정 예시로 강화석 가용량이 `100개`, 장비 한 단계 비용이 `20개`, 스킬 한 단계 비용이 `10개`라면 `20×장비 단계 + 10×스킬 단계 ≤ 100`이어야 합니다. 장비 5단계와 스킬 10단계는 `200개`를 요구하므로 동시에 도달했다고 계산할 수 없습니다. 각 모듈을 독립적으로 최고 단계에 퍼지 매칭하기 전에 배분 정책·우선순위를 정해야 합니다.

#### A. 잔여 압력과 실제 지갑을 분리하는 30일 검증

계획 소비가 공급보다 큰 경우라도 이미 소비한 실제 지갑이 음수라는 뜻은 아니므로, 운영 보고서에서 두 지표를 분리할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
5장 방식으로 30일 강화석 검증표를 작성해줘.
다음은 가정 데이터이며 단위는 강화석/30일, 모든 값은 활성 유저 1명 기준이다.
30일 계획 생산은 일일 보상의 누계 1,000과 이벤트 200으로 총 1,200, 계획 소비는 1,500이다.
초기 잔고는 400, 실제 유입은 1,200, 실제 지출은 1,050으로 별도 기록했다.
잔여량과 잔여 비율은 계획 생산·계획 소비만으로 계산하고, 소비 0의 정의도 적어줘.
실제 기말 잔고는 초기 잔고+실제 유입−실제 지출로 따로 계산해줘.
책의 검증 절차와 이 가정에서의 결과를 구분하고, 반올림은 비율 소수점 첫째 자리로 해줘.
필수 진행 재화라는 가정에서 부족 위험, 누적 위험, 확인할 추가 데이터를 각각 제시해줘.
잔여 비율을 엥겔 계수 R1 구간으로 환산하거나, 원문의 −50%를 모든 재화의 통과 기준으로 쓰지 마.
산출물은 식·표·판정·검수 체크리스트 순서로 제시하고 성공 기준도 수치로 써줘.
```

</details>

> **확인 포인트**
>
> 결과에서 계획 잔여는 `-300`, 잔여 비율은 `-20.0%`, 실제 기말 잔고는 `550`인지와 두 값을 서로 대체하지 않았는지를 확인합니다.
>
> 원문은 R1 구간과 음수인 잔여 비율을 어떻게 대응시키는지 밝히지 않으므로(인쇄 185 / PDF 215), `-20.0%`를 R1 구간으로 환산하지 않아야 합니다. 원문의 `-50%`도 불변 임곗값이 아닌 설계 출발점으로만 언급하는지 확인합니다.

<a id="ch05-b"></a>

#### B. 퍼지 매칭과 공유 재화를 함께 푸는 성장 경로

경험치로 레벨을 정하고 두 성장 모듈이 같은 자원을 쓰는 RPG에서, 독립 조회가 만들어 내는 불가능한 조합을 찾을 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
5장의 레벨·성장 검증으로 아래 가정 데이터를 계산해줘.
누적 경험치 기준은 레벨 1=0, 레벨 2=100, 레벨 3=260, 레벨 4=500, 레벨 5=850이며 오름차순이다.
30일 누적 경험치 620의 퍼지 매칭 결과와 최저·최고 구간 처리 규칙을 보여줘.
공유 강화석 가용량은 160개이고 장비 누적 비용은 단계 0=0, 1=40, 2=100, 3=180이다.
스킬 누적 비용은 단계 0=0, 1=30, 2=70, 3=120이며 장비 우선 배분을 가정한다.
각 모듈을 독립적으로 최고 단계에 매칭한 잘못된 결과와, 합계 소비≤160 제약을 적용한 결과를 비교해줘.
기간 시작 재고는 0, 공유 160개는 기간 생산량, 이후 추가 생산과 해금 제한은 없다고 가정해줘.
도달 레벨, 가능한 장비/스킬 단계 조합, 남은 재화, 후속 입력 요구 사항을 표로 작성해줘.
실제 레벨이 기대 레벨과 다르면 경험치 식을 고치기 전에 빠진 생산 루트부터 찾는 순서를 후속 확인 항목으로 적어줘.
책 근거 절차와 공유 재화를 위한 추가 제약을 분리해 설명하고 모든 단계는 정수로 처리해줘.
```

</details>

> **확인 포인트**
>
> 레벨은 `4`입니다. 독립 최고 조회인 장비 2·스킬 3은 비용 `220`으로 불가능하고, 장비 2·스킬 2도 `170`으로 초과합니다. 장비 우선 배분이면 장비 2·스킬 1, 소비 `130`, 잔여 `30`인지 확인합니다.
>
> 이 입력은 누적 경험치 기준을 직접 주므로 원문의 경험치 수정식(`경험치 = 단일 레벨 시간 × 캐릭터 레벨² × 보정값 + 매개변수`, 인쇄 187 / PDF 217)을 적용하지 않습니다. 원문은 실제 레벨이 기대 레벨과 다를 때 주로 수치 구조가 모든 생산 루트를 포함하지 못했기 때문이라고 보므로(인쇄 187 / PDF 217), 차이가 나면 빠진 생산 루트를 먼저 찾는지 봅니다.

#### C. 같은 성장 경로의 PvE·직업 PvP 동시 검증

경제 결과가 만들어 낸 유저 템플릿을 전투식과 연결해, 직업 문제와 보상 문제를 구별할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
5장의 경제→성장→전투 역방향 검증을 작성해줘.
가정상 14일 차에 전사와 궁수 모두 공격력 120, 방어력 90, 체력 300에 도달한다.
PvE 적은 방어력 100, 체력 600이고 단순 피해식은 공격력−방어력, 최소 피해는 1이다.
두 직업의 공격 속도는 초당 1.5회, 첫 타격은 0초, 치명·회복·회피는 없다.
PvP는 상대 방어력 90, 체력 300으로 두 직업을 같은 조건에서 비교해줘.
타격 수는 올림 처리하고 처치 시각은 (타격 수−1)/공격 속도로 계산해줘.
생존 턴 비율과 1회 피해 비율을 함께 쓸 때는 서로 다른 열·식으로 분리하고, 원문 표 5.15의 피해식이 이 단순식으로 재현된다고 주장하지 마.
이 결과가 직업 밸런스인지 동일한 입력의 산술적 동률인지 구분하고, 실제 차이를 검증할 추가 속성도 적어줘.
14일 차 속성이 경제 생산·소비에서 왔다는 가정과 책 근거인 검증 순서를 분리해줘.
산출물은 PvE/PvP 표, 단위, 성공 기준, 회귀 테스트 경계값으로 구성해줘.
책의 유저군 예시값을 인용한다면 본문 예시와 표 5.14의 값이 서로 다르다는 점을 표시해줘.
```

</details>

> **확인 포인트**
>
> PvE는 1회 피해 `20`, 30회, 약 `19.33초`이며 PvP는 1회 피해 `30`, 10회, `6.00초`로 계산되는지와 동률의 해석을 확인합니다.
>
> 책의 유저군 값을 인용할 때는 본문 예시(첫째 날 활성 유저 40레벨·전투력 5만pt, 인쇄 195–196 / PDF 225–226)와 표 5.14(1일 활성 42레벨·전투력 11,374, 인쇄 199 / PDF 229)가 서로 다른 원문 예시값이므로, 하나를 확정값으로 말하지 않는지 봅니다.

#### D. 상한·0 소비·구간 경계를 고정하는 회귀 검산

스프레드시트 수식이나 게임 서버 변경 뒤 조회·잔여 계산이 조용히 바뀌지 않았는지 확인할 때 씁니다.

<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
```

```text
각 판정이 유지되거나 바뀐 이유, 새로 찾은 반례, 다음에 확인할 자료를 마지막에 남겨줘.
```

> **확인 포인트**
>
> 후속 결과는 B의 기준선인 레벨 `4`, 장비 2·스킬 1, 소비 `130`, 잔여 `30`에서 출발해야 합니다. 변경 후 숫자만 제시하지 않고, 어떤 입력을 다시 수집해야 가정을 실제 데이터로 바꿀 수 있는지까지 남겨야 합니다.

### 산출물과 검수 기준

- 산출물은 기간별 생산·소비·잔여 표, 레벨·성장 모듈 매핑, 유저 템플릿, 전투 결과 표입니다.
- 누적 생산에서 일일 소비를 빼는 등 서로 다른 기간을 섞지 않았는지 봅니다.
- 퍼지 매칭 기준 열이 오름차순인지, 최저·최고 구간과 초기 경험치를 처리했는지 확인합니다.
- 모든 유저군에 같은 성장 경로를 강제하지 않고 활성·소과금·중과금·헤비과금 등 실제 세그먼트 정의를 적용합니다. 원문도 5장에서는 지면상 활성 유저의 검증만 설명하며, 실제 게임에서는 과금 수준별로 검증해야 한다고 씁니다(인쇄 188 / PDF 218).
- 전투 실패가 공식 문제인지, 실제 도달 속성·보상·비용 문제인지 분리합니다.
- 비용 행이 현재 레벨까지의 누적값인지 다음 도달 레벨 비용인지 고정합니다. 원문 표 5.15의 ‘생존 비율’은 각주상 1회 피해 비율이므로 생존 턴 비율로 자동 치환하지 않습니다. 원문 레벨값·그래프 범례의 불일치는 [조회·검증 조건](../.agents/skills/game-balance-bible/chapters/ch05-validation.md#검증-표의-연결-계약)과 원문 페이지 지도에서 확인합니다.

### 다른 장과 잇기

5장은 1장의 전체 루프에서 수정 결정을 만드는 관문입니다. 3장에 유저·몬스터 템플릿을 되돌리고, 4장의 생산·소비 가정을 고치며, 6장의 충전·소비 변경을 같은 경로에서 검증합니다. 7장에는 시간축 결과를 단계 목표와 리듬 그래프로 넘깁니다.

## 6장 — 게임의 수익화: 지표·결제·소비가 경험을 바꾸는 경로 확인하기

### 사용할 상황

- 상품·충전·뽑기·유도 결제의 위치와 게임 내 소비를 검토할 때
- ARPU, ARPPU, 결제율, LTV, CPA 등 지표를 하나의 보고서에서 비교할 때
- 결제 변경이 성장 격차, 경제 잔여, 전투 리듬에 미치는 영향을 분석할 때

### 준비할 입력

- 수익화 포지셔닝, 상품·가격·지급물·사용처·보장 조건, 변경 전후 기간
- 지표 정의, 모집단, 집계 기간, 제외 유저, 통화·환불 처리 기준
- 충전 유저군과 게임 내 소비 데이터, 성장·경제·전투 검증 결과

### 사용 전략

1. 경험·성장·기능·화폐 결제 가운데 변경이 무엇을 제공하는지 먼저 분류합니다.
2. 충전과 게임 내 소비를 별도 흐름으로 적습니다. 구매량이 늘어도 실제 소비처·가치 체계가 바뀌지 않을 수 있습니다.
3. 각 지표에 분자·분모·모집단·기간을 붙입니다. 예를 들어 과금 유저 평균과 전체 유저 평균을 섞지 않습니다.
4. 비과금·소과금·헤비과금 같은 유저군별 성장 경로와 경제 잔여를 비교하고, 전투 격차를 5장에서 다시 확인합니다.
5. 이벤트형 상품은 책의 5단계 운영법에 따라 목적 → 형식 → 참여 조건 → 주기 → 콘텐츠를 정의합니다. 월간 패스와 순위 이벤트를 비교한다면 목표 지표, 참여 횟수, 보상 소모 기간을 각각 적습니다.
6. 결과가 좋거나 나쁘다는 결론 전에 수익화가 핵심 플레이를 앞당기는지, 막는지, 선택을 넓히는지 확인합니다.

비교할 모든 시나리오는 같은 상품 기간과 동일한 과금 유저 정의를 사용합니다.

#### A. KPI 분모·기간을 고정한 ARPU와 근사 LTV 검증

월간 보고서에서 결제 지표와 이탈 지표를 비교하되, 서로 다른 코호트나 기간을 섞지 않을 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
6장 수익화 지표 검증표를 작성해줘.
다음은 가정 데이터이며 월간 활성 유저 10,000명, 월 과금 유저 500명, 월 총결제액 15,000 통화다.
월 이탈률은 월초 활성 코호트 기준 20%이며, 그 코호트와 월간 활성 정의가 일치한다고 가정한다.
금액은 같은 가상 통화 단위이고 15,000은 환불·세금을 제외한 순결제액이다.
PR, ARPPU, ARPU를 분자·분모·단위·기간과 함께 계산해줘.
근사 LTV는 월 ARPU×(1÷월 이탈률)만 사용하고, 이탈률 0일 때는 계산하지 마.
이 LTV가 ARPU와 이탈률이 매월 일정하다는 가정의 참고치임을 명시하고, 상한이나 하한으로도 단정하지 마.
ARPU를 쓴 이 근사식이 원문 본문 식 그대로인지 스킬의 해석인지 구분해 밝혀줘.
손익분기월은 이 입력만으로 계산하지 말고, 필요하면 월차별 코호트 수·수익·비용·누적 잔액을 별도 입력 계약으로 제시해줘.
가입자 전체, 신규 가입자, 과금 유저만의 지표와 혼동할 수 있는 오류를 표로 분리해줘.
책의 지표 정의·근사와 이 가상 코호트 데이터를 구분하고, 성공 기준과 추가 관측 항목을 제안해줘.
```

</details>

> **확인 포인트**
>
> PR `5.0%`, ARPPU `30`, ARPU `1.5`, 근사 LTV `7.5`인지와 LTV를 확정 예측처럼 표현하지 않았는지를 확인합니다.
>
> 원문 이탈률 식의 분모는 ‘총 유저 수’이며, 원문 예시는 월초 유저 수를 분모로 씁니다(인쇄 207 / PDF 237). 이 예시에서는 월초 활성 코호트가 그 자리에 들어간다는 가정이 결과에 적혀야 합니다. 원문은 실제 생명주기가 예측보다 훨씬 길다는 경고와 결제액이 시간이 갈수록 줄어든다는 경고를 함께 두므로(인쇄 208–209 / PDF 238–239), 근사 LTV `7.5`를 상한이나 하한으로 읽지 않는지도 봅니다.
>
> 원문 본문 식은 `활성 유저의 평균 결제율 × (1 ÷ 주기 이탈률)`이며(인쇄 209 / PDF 239), ARPU로 읽는 것은 표 6.1의 계산과 단위를 맞추려는 스킬의 해석입니다. 결과가 `ARPU÷이탈률`을 저자의 식으로 단정하지 않는지 확인합니다.

#### B. 상품 시나리오와 가중 ARPPU 민감도 분석

과금 유저 세그먼트 비중 하나에 기대지 않고, 구매 가정이 바뀔 때 상품 조합이 어떻게 달라지는지 볼 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
6장의 충전 검증 방식으로 가중 ARPPU 시나리오를 계산해줘.
가정상 과금 유저 세그먼트는 라이트 75%, 미드 20%, 헤비 5%이고 각 기간 구매액은 12, 40, 100 통화다.
기준 가중 ARPPU를 계산하고, 헤비 비중이 2%와 8%가 되는 두 민감도 시나리오를 별도 계산해줘.
헤비 비중은 2% 또는 8%로 고정하고, 남은 비중은 라이트:미드=75:20으로 배분해 합계 100%를 맞춰줘.
재정규화된 비중과 각 시나리오 ARPPU를 표로 적고 최종 금액만 소수점 둘째 자리로 반올림해줘.
상품은 성장 결제라는 가정이며, 가격·가치·구매 중복·환불 데이터는 아직 없다고 표시해줘.
책의 충전 검증 절차와 이 세그먼트 숫자가 프로젝트 가정이라는 점을 분리해줘.
결과는 산식, 가정표, 시나리오 표, 위험, 실제 데이터로 검증할 성공 기준 순서로 작성해줘.
ARPPU의 분모가 과금 유저이고 활성 유저 PR과 별도라는 검수 항목도 넣어줘.
```

</details>

> **확인 포인트**
>
> 기준 가중 ARPPU는 `22`, 헤비 2%는 약 `19.54`, 헤비 8%는 약 `24.46`입니다. 헤비 비중을 고정하고 나머지를 75:20으로 나눴는지 확인합니다.
>
> 원문은 충전 검증을 유저별 구매 경로로 집계하는 방식과 과금 수준별 결제 데이터를 표로 시뮬레이션하는 방식으로 할 수 있다고 하고, 후자를 예로 듭니다(인쇄 219 / PDF 249). 이 예시는 후자의 시뮬레이션이므로, 결과가 가중 ARPPU를 실제 유저별 결제 집계처럼 쓰지 않는지 확인합니다.

<a id="ch06-c"></a>

#### C. 5단계 운영법으로 7일 이벤트를 설계·검증

목적이 불분명한 할인이나 패스를 복제하지 않고, 이벤트의 참여 경험과 측정 지표를 연결할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
6장의 5단계 운영법으로 7일 성장 패스 가정안을 검토해줘.
목표는 활성 유저 결제율(PR) 변화 관찰 하나이며, ARPPU나 순위 경쟁은 성공 지표에서 제외한다.
대상은 튜토리얼 완료 후 7일 이내의 활성 유저, 참여 조건은 패스 1회 구매다.
보상은 즉시 성장 재화 100과 매일 재화 20×7일이며 단위는 재화/계정이다.
이벤트 목적·형식·참여 조건·주기·콘텐츠를 표로 고정하고, 각 항목의 실패 신호를 적어줘.
이 패스의 소비 동력이 책의 분류로 압박(push)인지 유인력(pull)인지 판정하고 근거를 적어줘.
무료 진행을 막지 않는지 판단할 실제 진행·이탈·경제 데이터가 없다는 점을 가정으로 표시해줘.
PR의 분자·분모·7일 관찰 기간과 대조군 정의를 제안하되 효과를 사실처럼 단정하지 마.
책의 5단계 프레임과 이 이벤트 숫자·운영안은 구분하고, 성공 기준과 중단 기준을 함께 작성해줘.
```

</details>

> **확인 포인트**
>
> `100+20×7=240` 재화인지와 PR 외의 목표를 몰래 합쳐 평가하지 않았는지, 대조군과 기간이 명시됐는지 확인합니다.
>
> 책은 ‘안 사면 손해’인 시간 제한 패키지와 ‘안 사면 없어짐’인 기간 한정 패키지를 압박(push)으로, 평생 한정 구매·프리미엄 패키지·탈것·아바타를 유인력(pull)으로 나눕니다(표 6.4, 인쇄 221 / PDF 251). 대상 유저가 튜토리얼 후 7일 이내로 한정되는 이 패스를 압박 쪽으로 판정하고, 그 근거로 구매 기간의 제한을 드는지 확인합니다. 성장 패스는 보통 과금 유저 그룹이 대상이고(인쇄 214 / PDF 244) 시즌 패스는 과금·비과금 유저 모두가 보상을 받으므로(인쇄 214–215 / PDF 244–245), 둘의 대상을 섞지 않아야 합니다.

<a id="ch06-d"></a>

#### D. 충전량과 게임 내 소비 압력을 분리하는 영향 분석

상품 지급이 늘어도 성장 소비처와 전투 격차가 어떻게 바뀌는지 자동으로 알 수 없을 때 씁니다.

<details>

### 산출물과 검수 기준

- 산출물은 포지셔닝 표, 지표 정의서, 충전·소비 흐름, 유저군별 영향 표입니다.
- 책의 기본 지표인 이탈률(CHURN)·PR·ARPPU·ARPU·LTV·CPA(인쇄 207–209 / PDF 237–239)를 동일한 모집단·기간이라고 가정하지 않습니다. DAU·MAU는 책에 정의가 없는 일반 지표이므로, 쓰려면 프로젝트의 정의를 따로 적고 책의 지표와 구분합니다.
- 서로 다른 통화·환불·중복 결제 처리 기준을 더하지 않았는지 확인합니다.
- ‘과금 유저 평균이 상승했다’만으로 성장 경험이나 공정성이 개선됐다고 결론 내리지 않습니다.
- `ARPU=PR×ARPPU`는 같은 기간·같은 활성 모집단과 결제액 정의에서 검산합니다. PR은 백분율 표시를 소수로 바꿔 사용합니다.
- 단순 LTV 근사 `ARPU/주기 이탈률`은 스킬의 해석입니다. 원문 본문 식은 `활성 유저의 평균 결제율 × (1 ÷ 주기 이탈률)`이며(인쇄 209 / PDF 239), 표 6.1의 계산과 단위를 맞추려고 ARPU로 읽습니다. ARPU와 이탈률의 관측 주기를 맞추고 일정하다는 가정을 적습니다. 이탈률이 0이면 식이 정의되지 않으며, 원문의 표현 불일치는 [원문 페이지 지도](../.agents/skills/game-balance-bible/references/source-map.md)에 기록되어 있습니다.
- 책의 사례 수치나 결제 방식은 현재 시장의 기준으로 단정하지 않습니다. 원문의 CPA 사례 범위와 플랫폼별 값(인쇄 210 / PDF 240)도 획득 기준이 밝혀져 있지 않으므로, 프로젝트의 CPA를 높다·낮다고 판정하는 기준으로 쓰지 않습니다. 원문은 유도 결제가 게임의 표준이 됐다고 하면서도, 고품질 게임은 이 관행을 무시할 수 있었다고 덧붙입니다(인쇄 213 / PDF 243). 따라서 유도 결제를 필수 요건으로 판정하지 않습니다.
- 월간 패스는 그 기간의 리텐션이 가장 큰 목적입니다. 일반·프리미엄 가격 차별에는 일반 월간 패스의 수익을 프리미엄보다 높여 일반을 맛보기 상품으로 두는 방식과 프리미엄의 수익·가성비를 훨씬 높이는 방식이 있고, 매일 로그인할 때마다 초과 보상이나 차별 서비스를 넣을 수 있습니다(인쇄 214 / PDF 244). 여기서 ‘수익’을 유저가 받는 보상 비율로 읽는 것은 스킬의 해석입니다. 보상 패키지는 구매 간격에 따라 일일/주간/월간 패키지, 평생 패키지, 조건 패키지로 나뉘며, 그 기간에 유저가 필요로 할 자원을 미리 예측합니다(인쇄 215 / PDF 245). 상품표에 어느 방식·종류인지 적습니다.
- 표 6.1의 손익분기월 산식은 원문에 없습니다. 실제 회수 시점은 코호트별 누적 수익·비용으로 계산하고, 본문과 상품표의 가격·구매 목록을 섞어 합산하지 않습니다.

### 다른 장과 잇기

4장의 가치 체계와 소비 모델이 수익화의 사용처를 만들고, 5장은 유저군별 실제 성장·전투 결과를 확인합니다. 7장은 상품·보상 시점이 리듬을 깨는지 보여 주며, 8장은 수익화 검증 모델의 입력·출력을 다른 모델과 연결합니다.

## 7장 — 수치 시각화: 그래프를 결론이 아니라 경험 가설로 쓰기

### 사용할 상황

- 특정 구간이 지루하거나 급격하게 어려워진다는 피드백을 시간축에서 살필 때
- 성장 해금, 보상, 전투 시간, 소비, 수익화의 시점을 조정할 때
- 긴 표를 보고도 콘텐츠 공백과 목표 과밀을 발견하기 어려울 때

### 준비할 입력

- 레벨·일차·세션 등의 공통 가로축과 콘텐츠·성장·보상·전투 데이터
- 단일 피해, 전투 시간, 성장의 질적·양적 변화, 해금·의례·보상 시점
- 어떤 유저군의 어느 구간을 보고 있는지와 플레이 테스트 또는 로그 근거

### 사용 전략

1. 목표 시간을 레벨·일차·세션 중 하나로 고정하고 다른 데이터를 같은 축에 정렬합니다.
2. 성장의 양적 증가와 질적 변화, 전투의 단일 피해와 전투 시간을 다른 행 또는 그래프로 둡니다.
3. 단계 목표는 단계 구분 → 해금 기능 검증 → 성장 리듬 검증 → 과금 깊이 검증 → 유저 목표 설정으로 구성합니다. 단계마다 시간·레벨·새 기능·소비량·목표를 한 행에 놓습니다. 책은 다섯 단계를 마친 뒤 그 과정에서 드러난 체감을 종합 평가해 경험 과정을 최적화하며, 체감에는 절대적인 정답이 없다고 봅니다(인쇄 235 / PDF 265).
4. 저점·과밀·급상승을 찾으면 보상값만 올리지 말고 해금, 소비, 난이도, 전투 시간을 원 모델에서 추적합니다.
5. 시간 변화는 꺾은선, 주기별 구성 비교는 막대, 한 시점의 전체 대비 비중은 원그래프로 구분합니다. 다른 단위는 별도 축·패널로 표시합니다.
6. 그래프의 가중치·흥미도는 가설로 표시하고 유저군별 플레이 테스트·검증 데이터로 교차 확인합니다.

### 가정 예시: 리듬 공백 찾기

가정 예시로 0~60분의 세션 표에 전투 스킬 해금, 장비 강화, 동료 해금, 희귀 보상 시점을 기록할 수 있습니다. 20~30분 사이에 질적 변화와 짧은 목표가 모두 없다는 점은 점검할 가설입니다. 그 공백을 새 보상으로 메울지, 전투 시간이나 강화 비용을 바꿀지는 3·4·5장의 계산을 다시 한 뒤 결정합니다.

#### A. 첫 60분의 질적·양적 성장 리듬 설계

튜토리얼 이후 보상이 몰리거나 비는 구간을, 기능 해금과 수량 보상을 같은 시간축에서 검토할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
7장 리듬감 관점으로 첫 60분 경험 가정안을 검토해줘.
양적 보상은 10분에 레벨업, 25분에 장비 강화, 45분에 레벨업이며 각 보상은 1회다.
질적 변화는 15분 전투 스킬, 35분 동료, 55분 희귀 보상 해금이다.
모든 시간은 첫 플레이 시작 후 분, 보상 집계는 횟수이며 실제 행동 완료율 데이터는 없다.
시간축 표와 꺾은선에 넣을 데이터 열을 설계하고, 보상 간격·동시 집중·공백을 계산해줘.
20~30분 구간을 포함해 리듬 저점 가설과 대안 두 개를 제시하되 새 보상은 가정으로 표시해줘.
의례 연출은 보상량 증가와 분리하고, 확인할 플레이 테스트 질문도 적어줘.
책의 리듬감 원리와 이 타임라인 가정을 구분하며 단위·반올림·성공 기준을 명시해줘.
```

</details>

> **확인 포인트**
>
> 질적 해금이 15·35·55분, 양적 보상이 10·25·45분으로 분산됐는지와 20~30분을 사실상 저점으로 단정하지 않았는지 확인합니다.

<a id="ch07-b"></a>

#### B. 30일 단계 목표와 해금·소비를 연결하는 설계표

레벨 표만으로는 보이지 않는 콘텐츠 갱신, 성장 목표, 과금 깊이의 관계를 한 표에서 검토할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
7장 단계 목표 5단계로 30일 가정 데이터를 설계해줘.
구간은 1~3일 튜토리얼, 4~10일 초보, 11~20일 성장, 21~30일 정체로 나눈다.
해금은 각 구간에 스킬, 장비 강화, 협동 던전, 상위 도전을 차례로 하나씩 배치한다.
가정상 각 구간 마지막 날의 게임 시작 후 누적 성장 재화 소비는 100, 300, 700, 1,200이다.
단위는 재화/활성 유저 1명이고, 각 구간 동안의 순증 비용을 따로 계산해줘.
각 단계에 시간·레벨 범위(미정이면 빈칸)·기능·중복 콘텐츠·흥미도 가설·성장 목표·소비·유저 목표를 표로 만들어줘.
흥미도는 몰입감의 변화이고 값이 높을수록 그 시점의 유저 경험이 좋다는 뜻이지 콘텐츠 양이 많다는 뜻이 아님을 표에 밝혀줘.
과금 깊이는 소비량 자체가 아니라 별도 가치 체계가 있어야 계산 가능하다고 표시해줘.
4장의 판매 가능 자원 비율 보정을 적용할지도 따로 적어줘.
단계 길이와 콘텐츠 신선도를 검증할 실제 행동·이탈 데이터 요구 사항을 적어줘.
5단계 뒤에는 다섯 단계에서 드러난 체감을 종합 평가하고 최적화할 항목으로 마무리하되, 체감에 절대 정답이 있다고 쓰지 마.
책의 단계 목표 절차, 프로젝트 가정, 다음 5·6장으로 넘길 검증 항목을 구분해줘.
```

</details>

> **확인 포인트**
>
> 구간 순증 비용은 `100·200·400·500`, 30일 총소비는 `1,200`인지 확인합니다. 기말 누계를 더해 중복 집계하거나, 가치 체계 없이 금액·매출을 산출하지 않습니다.
>
> 책은 다섯 단계를 마친 뒤 ‘마지막 단계’로 체감을 종합 평가해 경험 과정을 최적화하고, 체감에는 절대적인 정답이 없다고 봅니다(인쇄 235 / PDF 265). 결과가 표를 다섯 단계에서 끝내지 않고 종합 평가 항목을 남기는지, 그 평가를 확정 정답처럼 쓰지 않는지 확인합니다.
>
> 원문 노트는 단계를 만들 때 단계별 게임 주기를 정하는 것이 가장 중요하다고 합니다(인쇄 232 / PDF 262). 레벨 범위가 빈칸이어도 일 단위 구간이 단계 표의 기준으로 남는지 확인합니다. 4장의 과금의 깊이는 판매 가능 자원 비율로 정한 보정 매개변수를 곱하지만(인쇄 175 / PDF 205), 7장의 과금 깊이 검증은 이 보정을 언급하지 않습니다(인쇄 234 / PDF 264). 결과가 보정 적용 여부를 함께 적는지 봅니다.
>
> 원문은 각 시점의 흥미도를 유저의 몰입감 변화로 보고, 그림 7.3의 Y축 값이 높을수록 그 시점의 유저 경험이 좋다고 합니다(인쇄 233 / PDF 263). 결과가 흥미도 열을 콘텐츠 양이나 관측값으로 쓰지 않고 가설 가중치로 남기는지 확인합니다.

#### C. 질문별 그래프 선택과 동일 기준 비교

하나의 화려한 차트로 모든 문제를 설명하지 않고, 비교 대상과 시간축에 맞는 시각화 명세를 만들 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
7장의 그래프 선택법으로 네 가지 질문의 시각화 명세를 만들어줘.
질문은 일차별 성장 재화 변화, 모듈별 속성 기여 비율, 주차별 생산 구성, 직업별 여러 속성 경향 비교다.
가정 데이터 기간은 30일, 단위는 재화/일·속성점·비율이며 과금 유저와 전체 활성 유저를 섞지 않는다.
각 질문에 꺾은선·원·막대·레이더 중 적합한 그래프와 부적합한 그래프를 한 개씩 선택해 이유를 써줘.
같은 그래프에서 분자·분모·시간축·세그먼트·누적/일별 값을 고정하는 체크리스트를 만들어줘.
지수·선형·로그·다항식 추세는 데이터 가설을 설명하는 보조 수단으로만 쓰고 주기성을 단정하지 마.
네 곡선에 대한 저자의 평가와, 이 데이터에 어느 곡선이 맞는지의 판단을 다른 열로 나눠줘.
책의 선택 기준과 이 분석 조건을 구분하고, 각 차트가 발견한 이상을 어느 장 모델에 되돌릴지 연결해줘.
산출물은 질문→그래프→필수 열→판독 규칙→검증 경로 표와 성공 기준으로 작성해줘.
```

</details>

> **확인 포인트**
>
> 변화에는 꺾은선, 비율에는 원, 주기별 구성에는 막대, 다속성 경향 비교에는 레이더를 선택하는지와 동일 차트의 축 정의가 있는지 확인합니다.
>
> 책이 구분하는 곡선 4종은 지수·선형·로그·다항식이며(인쇄 235 / PDF 265), ‘주기적 곡선’을 따로 들지 않습니다. 저자는 선형을 보통 특정 성장 모듈에만 쓰고, 로그를 대부분의 게임 성장 추이로, 다항식을 경험상 가장 좋은 형태로 평가합니다(인쇄 236 / PDF 266). 이 평가가 이 데이터의 추세 판정을 대신하지 않고 다른 열에 남는지 확인합니다.

#### D. 실제 관측에서 리듬 저점을 진단하는 분석 요청

차트의 저점이 보상 부족, 전투 난이도, 측정 오류 중 무엇인지 성급히 결론 내리지 않고 진단 가설을 만들 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
7장 관점으로 아래 가정 관측을 진단해줘.
첫 60분 구간의 완료 세션 수는 10분 1,000, 20분 820, 30분 600, 40분 590, 50분 580이다.
15분에는 스킬 해금, 35분에는 동료 해금이 있었고, 보상 수량·난이도·오류 로그는 제공되지 않았다.
세션 수의 기준은 해당 분까지 도달한 익명 세션 수이며, 코호트·플랫폼 차이는 아직 미분리다.
직전 구간 대비 변화율=(현재−직전)/직전으로 소수점 첫째 자리 %를 계산해줘.
각 시점의 포함·제외 기준, 집계 시각, 중도 이탈·결측 처리 규칙이 없음을 재현성 결손으로 표시해줘.
20~30분 저점 가설을 최소 세 가지로 나눠줘.
보상 부족·난이도·측정 편향을 확정 원인으로 쓰지 말고 필요한 추가 이벤트 로그를 각 가설에 연결해줘.
리듬·의례·몰입 점수는 관측값이 아니라 추가 설문·테스트가 필요한 가설로 표시해줘.
책의 시각화 프레임과 이 합성 관측치를 분리하고, 3·4·5장에 보낼 재검증 순서를 작성해줘.
산출물은 계산표, 진단 가설, 추가 데이터, 조치 우선순위, 성공 기준 순서로 작성해줘.
```

</details>

> **확인 포인트**
>
> 10→20분 `-18.0%`, 20→30분 약 `-26.8%`, 30→40분 약 `-1.7%`인지와 30분 이전 감소를 단일 보상 문제로 단정하지 않는지 확인합니다.

> **확인 포인트**
>
> 후속 결과는 D의 변화율 `-18.0%`·약 `-26.8%`·약 `-1.7%`를 기준선으로 쓰고, 재현성 결손이 해소되기 전에는 실험 결과의 원인 판정을 미확인으로 둬야 합니다. 시각화 개선안을 실제 경험 개선으로 선언하지 않고, 동일한 관측 기준과 연결 모델의 재검증을 갖춰야 합니다.

### 산출물과 검수 기준

- 산출물은 공통 시간축 데이터 표, 단계 목표 표, 관찰·가설·검증 목록입니다.
- 전투 시간과 단일 피해, 성장 수익과 비용, 무료 공급과 과금 깊이를 서로 다른 단위로 혼합하지 않았는지 봅니다.
- 같은 시점에 모든 질적·양적 보상을 몰아넣어 이후 공백을 만들지 않는지 확인합니다.
- 그래프의 모양만으로 재미·이탈 원인을 확정하지 않고 플레이 검증 근거를 함께 둡니다.
- 전투 리듬의 이중축은 피해와 시간 단위를 각각 유지합니다. 원문 그림 7.1에서 어느 선이 어느 축인지는 범례에 없고 값 범위로 읽은 대응은 스킬의 해석이므로(인쇄 228 / PDF 258), 축 대응을 책의 서술로 인용하지 않습니다. 몰입 점수는 척도·출처·합산 규칙을 밝혀야 재현할 수 있습니다. 원문은 몰입감을 주로 리듬감과 의례감이 교차할 때 생기는 심리 변화로 보고, 주기별 리듬·의례 효과를 숫자로 바꿔 면적 그래프로 나타냅니다(인쇄 230 / PDF 260).

### 다른 장과 잇기

2장의 목표 경험은 7장의 관찰 기준이고, 3장의 전투 시간·4장의 비용과 보상·5장의 실제 성장 데이터·6장의 수익화 영향이 그래프의 입력입니다. 8장에서는 발견한 저점이 어느 모델의 문제인지 연결 관계로 좁힙니다.

## 8장 — 수치 모듈화: 변경 가능한 모델과 영향 범위 만들기

### 사용할 상황

- 장비·캐릭터·드롭·이벤트 같은 기능이 늘어나며 표와 공식의 출처가 불명확해질 때
- 비용 하나를 고쳤을 때 생산·성장·전투·수익화 중 어디를 재검증해야 하는지 정할 때
- 검증된 구조를 다음 콘텐츠나 프로젝트에 재사용하려 할 때

### 준비할 입력

- 현재 수치 모델 목록, 각 모델의 책임·입력·출력·상태·인터페이스·계산 로직
- 매개변수 원천, 다른 모델에서 호출하는 데이터, 갱신 주기와 소유자
- 변경 요청, 영향받을 유저 경험, 기존 검증 결과와 재검증 가능한 데이터

### 사용 전략

1. 10개 모델(기초 성장, 속성 성장, 성장 모듈 성장, 몬스터 난이도, 성장 소비, 생산, 경제 검증, 성장 검증, 수익화 검증, 전투 기본 모델)에 현재 자료를 배치합니다. 번호는 일방향 실행 순서가 아니며, 전투 기본 모델은 필요한 설계·검증 단계에서 호출합니다.
2. 각 모델은 설계 아이디어를 먼저 정리한 뒤 매개변수 정의 → 데이터 호출 → 모델 계산을 작성하고, 원천 데이터와 파생 데이터를 구분합니다. 책은 기능의 세부 사항을 요약해 아이디어를 명확히 한 뒤(인쇄 244–245 / PDF 274–275) 세 단계로 수치를 구한다고 설명합니다(인쇄 245–250 / PDF 275–280). 원문은 이 세 단계를 성유물 한 시스템으로 시연합니다. 스킬의 적용 지침: 다른 모델에도 같은 세 단계를 씁니다.
3. 입력·출력·단위·주기·상한·반올림·소유자를 계약으로 적습니다.
4. 변경한 모델에서 나가는 출력과 그 출력을 읽는 다음 모델을 따라가 재검증 목록을 만듭니다.
5. 재사용할 때는 숫자만 옮기지 않고 경험 목표, 인터페이스, 제약, 검증 순서를 함께 이식합니다. 저자는 어떤 수치를 완벽하게 복각하는 것도 우수한 게임 경험을 계승하는 방법이 될 수 있다고 봅니다(인쇄 251 / PDF 281).

[원문 성유물 예시](../.agents/skills/game-balance-bible/chapters/ch08-modularization.md#원문-성유물-예시-재현-가능한-입력과-계산)를 학습할 때는 출현 횟수·별 등급 비율·초깃값·돌파 횟수·부속성 변동 범위(70/80/90/100%, 표 8.7, 인쇄 247 / PDF 277)를 입력으로 구분합니다. 이 예시를 현재 게임 규칙으로 간주하지 않으며, 원문에 없는 부속성 선택 가중치·변동 후 반올림은 확정값으로 채우지 않습니다.

### 가정 예시: 모델 계약

가정 예시로 `공격력 = 초깃값 + (레벨-1)×레벨 증폭`이라는 성장 모델을 두면, 입력은 레벨과 두 매개변수, 출력은 공격력입니다. 초깃값 100과 레벨 증폭 50을 가정하면 레벨 10의 출력은 `100+(10-1)×50=550`입니다. 이 수치는 설명용이며, 실제 모델에는 레벨 범위·직업 보정·버프 적용 시점과 다른 모델이 읽는 공격력의 단위를 계약에 추가해야 합니다.

공통 검수에서는 모든 계약 필드에 이름·단위·허용 범위·소유 모델·버전을 붙입니다. 입력이 바뀌었을 때 어떤 출력과 어떤 테스트가 달라지는지 남기지 못하면 재사용 모델로 승인하지 않습니다.

모듈의 독립성은 입력을 무시해도 된다는 뜻이 아닙니다. 다른 모델을 호출하는 값은 출처와 산출 시점을 기록합니다. 반복 검증을 위한 피드백과, 같은 계산 회차 안에서 풀리지 않는 순환 참조를 구분합니다.

모델 번호는 책의 분류·의존 관계 기준입니다. 전투 기본 모델은 초기 속성 검증에도 쓰고, 몬스터 난이도는 실제 성장 검증 결과로 다시 보정합니다. 모든 계산을 번호대로 한 번만 실행하는 절차로 해석하지 않습니다.

검증 결과도 모델 계약의 출력으로 버전과 함께 보관합니다.

#### B. 매개변수·호출값·계산식의 수식 계보 추적

단순 성장식이라도 값의 출처를 추적해, 임의 상수와 다른 모델에서 넘어온 데이터를 구별할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
8장의 매개변수 정의→데이터 호출→모델 계산으로 장비 공격력 모델을 작성해줘.
그 앞에 이 모델의 설계 아이디어(목적·범위·제약)를 정리하는 단계를 두고, 정리한 아이디어가 어떤 매개변수로 이어지는지 보여줘.
가정 매개변수는 공격력 초깃값 100, 레벨 증폭 50, 레벨 10이며 단위는 공격력 점과 레벨이다.
기본 식은 공격력=초깃값+(레벨−1)×레벨 증폭으로 고정한다.
장비 모듈은 호출값인 전체 속성 성장 550의 20%를 배분받는다는 별도 가정을 둔다.
기본 식 결과와 배분값 550×0.20을 각각 계산하고, 둘을 자동 합산해도 되는지 계약 없이는 판단하지 마.
각 값에 정의 위치, 호출 원본, 계산 단계, 반올림, 상한, 다음 모델 전달값을 붙여줘.
책의 구축 순서(아이디어 정리 뒤 3단계)와 이 수치 예시를 구분하고, 단위 불일치·순환 호출·상수 하드코딩 검사도 넣어줘.
원문은 3단계를 성유물 한 시스템으로 시연했으니, 이 장비 모델에 쓰는 것은 스킬의 적용 지침으로 표시해줘.
산출물은 수식 계보 표, 계산 검산, 계약 위반 사례, 성공 기준 순서로 작성해줘.
```

</details>

> **확인 포인트**
>
> 기본 식은 `550`, 배분 호출값은 `110`인지와 둘을 같은 의미의 공격력으로 중복 합산하지 않는지 확인합니다.
>
> 책은 기능의 세부 사항을 요약하고 설계 아이디어를 명확히 한 뒤(인쇄 244–245 / PDF 274–275) 매개변수 정의·데이터 호출·모델 계산의 세 단계로 수치를 구한다고 설명합니다(인쇄 245–250 / PDF 275–280). 결과가 매개변수 정의부터 시작하지 않고 아이디어 정리를 앞에 두는지 확인합니다.
>
> 원문은 이 세 단계를 성유물 한 시스템으로 시연합니다(인쇄 245–250 / PDF 275–280). 결과가 장비 공격력 모델에 같은 절차를 쓰는 것을 원문의 시연이 아니라 스킬의 적용 지침으로 표시하는지 봅니다.

#### C. 소비 비용 변경의 영향 범위와 검증 순서

한 모듈의 숫자만 바꿨을 때 성장·경제·수익화·전투에서 다시 확인할 순서를 정할 때 씁니다.

<details>
<summary><strong>프롬프트 펼치기 · 복사</strong></summary>

```text
$game-balance-bible
장비 강화 1단계 비용을 가정상 40에서 50 재화로 바꾸는 변경 영향 분석을 해줘.
변경 대상은 5단계 성장 소비 모델이며, 생산량·성장 속성·상품 지급·몬스터 표는 아직 변경하지 않았다.
재화 단위는 재화/강화 1단계, 기간·유저군·초기 재고는 실제 데이터가 없어 미정이다.
8장의 의존 순서에 따라 직접 영향, 간접 영향, 영향 없음(가정상)을 구분해줘.
먼저 재계산할 모델과 그다음 검증 모델을 번호와 이유로 제시해줘.
모델 7(경제 검증)의 잔여, 모델 8(성장 검증)의 실제 성장,
모델 9(수익화 검증), 모델 10(전투 기본)의 결과에서 필요한 입력과 통과 기준을 적어줘.
그림 8.1에 있지만 본문이 설명하지 않는 모델 5→1 연결은 영향 여부를 미확인으로 표시해줘.
40→50의 증가율을 소수점 첫째 자리 %로 계산하고, 재화 부족을 곧바로 결제 압박으로 해석하지 마.
책의 연결 원리, 변경값, 미정 데이터, 추가 제안을 분리한 변경 명세서로 작성해줘.
```

</details>

> **확인 포인트**
>
> 증가율 `25.0%`인지와 생산·소비·성장 검증을 거치지 않고 수익화나 전투 결과를 단정하지 않는지 확인합니다.
>

### 산출물과 검수 기준

- 산출물은 10단계 맵, 모델 계약 표, 데이터 계보, 변경 영향·재검증 목록입니다.
- 한 모델의 입력이 다른 모델에서 중복 정의되지 않고 원천이 명시됐는지 확인합니다.
- 비용 변경 뒤 생산·경제 검증만이 아니라 성장·전투·수익화 영향을 포함했는지 확인합니다.
- 독립성을 고립으로 오해해 연결 모델의 재검증을 빼지 않았는지 확인합니다.
- 모델 계약에 단위·기간·상한·반올림·유저군 조건이 빠지지 않았는지 확인합니다.
- 원문 성유물 표를 재현할 때 표 8.10의 1~4성 초깃값 `9% / 11% / 12% / 14%`는 원문 표기이고(인쇄 248 / PDF 278), 누적 비율 재현식은 스킬 검산입니다. 치유 보너스 부속성은 표 8.4의 총합 4(인쇄 246 / PDF 276)와 달리 표 8.8에서 0.0%이고 표 8.11에는 열만 있고 값이 비어 있으므로(인쇄 247·249 / PDF 277·279), 빈 값을 채우거나 한 표에 맞춰 고치지 않습니다. 표 8.9는 3~5부위 원소 마스터리를 `84.15`로 싣지만(인쇄 248 / PDF 278), 스킬 검산으로 표 8.3의 출현 횟수 3(인쇄 245 / PDF 275)을 넣으면 `28.05`입니다. 재현할 때는 원문 표기와 계산값을 함께 적습니다.

### 다른 장과 잇기

8장은 1장의 5단계 프로세스를 구현 구조로 바꿉니다. 3~6장의 모델을 각각 10단계 체계에 연결하고, 7장에서 발견한 경험 문제를 특정 모델·입력·출력으로 되돌립니다. 변경 후에는 [검수와 테스트](validation.md)의 원문 대조·독립 계산·호스트 사용 시험을 적용합니다.

## 장을 연결하는 실무 흐름 세 가지

세 흐름은 각각 신규 적용, 기존 문제 개선, 변경 후 검증에 대응합니다. 장을 읽는 순서는 이 가이드가 제안하는 작업 순서이며 책이 정한 절차가 아닙니다. 장별 예시의 결과를 이어 붙일 때는 [프롬프트를 고르고 결과를 이어가는 방법](#prompt-workflow)의 4번 항목처럼 선행 결과와 조건 판정을 함께 적습니다.

<a id="integrated-1"></a>

### 1. 신규 콘텐츠의 전투·보상 설계

아직 수치가 정해지지 않은 신규 콘텐츠에 목표 경험부터 모델 계약까지 처음 적용하는 **신규 적용** 흐름입니다.

1. 2장에서 목표 경험과 유저·콘텐츠 구간을 정합니다.
2. 3장에서 목표 전투 시간, 속성, 대미지·확률 플로, NPC 템플릿을 만듭니다.
3. 4장에서 성장 비용과 보상·드롭 I/O를 같은 주기로 연결합니다.
4. 5장에서 실제 도달 속성과 전투 결과를 유저군별로 검증합니다.
5. 7장에서 보상·해금·전투 시간의 시간축을 읽고, 8장 계약에 변경 이력을 남깁니다.

### 3. 수익화 변경의 영향 검증

상품이나 결제 구조를 바꾼 뒤 그 변경이 경제·성장·전투·리듬에 미친 영향을 확인하는 **변경 후 검증** 흐름입니다.

1. 6장에서 상품이 경험·성장·기능·화폐 중 무엇을 바꾸는지와 지표의 기간·모집단을 정의합니다.
2. 4장에서 지급물과 소비처가 경제 총량·가치 체계에 더하는 변화를 계산합니다.
3. 5장에서 비과금·과금 유저군의 도달 레벨, 잔여 재화, 전투 결과를 같은 기간으로 비교합니다.
4. 7장에서 상품·보상 시점이 핵심 루프의 리듬과 단계 목표를 과도하게 앞당기거나 막는지 읽습니다.
5. 8장에서 충전·소비·경제·성장·전투 모델을 다시 실행할 변경 목록으로 기록합니다.

## 결과를 다음 단계에 넘기기 전 확인할 것

| 확인할 항목 | 결과에 남아 있어야 할 근거 |
|---|---|
| 출처 | 사용한 장·참고 파일과 프로젝트 데이터, 새 가정의 구분 |
| 계산 | 변수·단위·기간·모집단·중간식·반올림과 핵심 합계 |
| 범위 | 입력이 빠져 계산하지 못한 항목, 식의 적용 조건과 경계값 |
| 변경 | 고정한 조건, 바꾼 매개변수, 전후 비교와 다음 장에 전달할 값 |
| 검증 | 독립 검산 또는 실험 결과, 통과·실패 기준과 남은 플레이 검증 |

> [!IMPORTANT]
> **다음 단계로 넘기는 기준**
>
> 데이터가 부족한 항목은 가설로 유지합니다. 계산의 정합성과 실제 플레이 경험을 함께 확인한 뒤 적용 여부를 결정합니다.
