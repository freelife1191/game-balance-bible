# 기법과 적용 절차

## 5단계 수치 프로세스 — Ch 1
**언제**: 신규 게임의 수치 구조를 처음 만들 때.
**방법**: 준비 → 전투 → 경제 → 검증 → 수익화로 입력과 산출물을 연결하고, 검증 결과를 앞 단계로 되돌린다.
**절충**: 출시 일정상 일부는 병행하더라도 기반 정의를 생략하면 뒤 단계에서 다시 계산해야 한다.

## 타깃 게임 구조 추출 — Ch 2
**언제**: 비교할 성공 사례가 있으나 수치를 그대로 복사하기 어려울 때.
**방법**: 장르·테마·유저 특성을 정하고, 기준 게임의 육성·플레이·전투 구조와 주기를 뽑아 목표 경험에 맞게 변환한다.
**절충**: 검증된 구조를 참고할 수 있지만 프로젝트의 이용자·규모와 연결 조건이 다르면 수치도 바뀐다.

## 전투 판정과 수익곡선 검증 — Ch 3
**언제**: 치명타·회피·관통 증가가 실제 성능과 다르게 느껴질 때.
**방법**: 기초·스킬·대미지 플로 작성 → 판정 우선순위 확정 → 확률론/원탁 선택 → 기대 피해와 속성별 수익곡선 비교.
**절충**: 순차 판정은 조합이 다양하지만 후순위 효과의 실제 빈도가 감소한다. 원탁은 서로 배타적인 결과를 구성하며 합계와 우선순위를 관리해야 한다.

## 성장 구축·분할·세분화 — Ch 3
**언제**: 장비·스킬·수집 시스템을 성장 구조에 추가할 때.
**방법**: 기준 성장 곡선 → 시스템별 성장 몫 → 레벨·등급·부위별 세부 배분 → 총속성과 전투 검증.
**절충**: 합계가 맞아도 해금·성장 간격이 어긋나면 경험 리듬은 깨진다.

## I/O 경제 지도 — Ch 4
**언제**: 재화의 공급 과잉·소비처 부족 또는 거래 악용을 찾을 때.
**방법**: 모든 화폐·자원을 나열 → 생산·변환·거래·소비 루트 연결 → 연결 표/블랙닷 구조 표 작성 → 가치와 비용을 공통 기준으로 환산.
**절충**: 유통을 열면 상호작용이 늘지만 생산·가격 통제와 거래 규칙의 관리도 필요하다.

## 경제→육성→전투 역방향 검증 — Ch 5
**언제**: 설계상 기대 레벨·난이도와 실제 유저 경험이 다를 때.
**방법**: 누적 계획·추가 생산과 소비 집계 → 잔여량/비율 → 누적 경험치·비용을 테이블에 퍼지 매칭 → 도달 레벨의 속성 → PvE/PvP 결과.
**절충**: 한 유저가 공유 자원을 여러 시스템에 쓰면 전체량을 각 시스템에 중복 투입하면 안 된다. 지표는 같은 기간·유저군으로 맞춘다.

## 5단계 운영법 — Ch 6
**언제**: 패스·충전 이벤트·기간 상품을 설계할 때.
**방법**: 이벤트 목적 → 형식 → 참여 조건 → 주기 → 콘텐츠를 정하고, 직접 충전과 게임 내 화폐 소비를 유저군별로 검증한다.
**절충**: 결제율·활동·리텐션·객단가 목표가 충돌할 수 있다. 운영 효과를 성장·전투 검증과 함께 본다.

## 단계 목표와 곡선 대조 — Ch 7
**언제**: 초반 몰입 또는 중후반 성장이 끊길 때.
**방법**: 유저 단계 구분 → 목표와 달성 시간 설정 → 경험 리듬 예상 → 성장·소비·난이도 곡선을 같은 시간축에 비교.
**절충**: 선형은 예측 가능하고, 지수는 부담이 빠르게 커지며, 로그는 뒤로 갈수록 증가폭이 줄어든다. 목표 경험에 맞춰 조합한다.

## 수치 모듈 구축과 교체 — Ch 8
**언제**: 시스템 변경의 영향을 좁히거나 검증된 육성 모델을 재사용할 때.
**방법**: 매개변수 정의 → 데이터 호출 → 모델 계산. 입력·출력과 의존 모델을 명시하고 변경 후 연결 모델의 검증을 반복한다.
**절충**: 모듈 분리만으로 전체 경험의 독립성이 생기지는 않는다. 성장 예산·경제 가치·전투 리듬의 접점을 보존한다.

## 계산 실행 검산 — 실무 보완
**언제**: 사용자가 실행 검산을 요청하거나, 확률 분포·단계 조회·공유 지갑 조합을 계산 도구로 확인할 때. 개념 설명만 하는 요청에 실행을 추가할 필요는 없다.

- 같은 입력·단위·가정을 고정하고 사용 가능한 계산 도구로 핵심 식을 실행한다. 검산 코드를 제시한 것과 실제 실행을 구분한다.
- 결과에는 입력·핵심 식, 실행 방법, 실제 관측 출력, 통과/불일치/미실행 판정을 남긴다. 출력이 없으면 추론한 값을 실행 결과로 대체하지 않는다.
- 조회·공유 지갑 조합은 비용 제약을 충족하는 목록과 잔여량을 계산한 뒤 개수를 구한다. 기대 개수 하나를 맞추는 대신 경계·누락·중복과 합계 소비를 확인한다.
- 실행이 실패하면 원인을 고쳐 실제 재실행한 결과로 판정한다. 해결하지 못한 실패와 미실행은 남기고, 확인한 범위까지만 결론낸다. 실제 게임 적용·승률·사용자 경험은 별도 검증이다.

이 절차는 책의 공식에 적용하는 실무 보완이며 원문에 제시된 검증 프로세스와 구별한다.
